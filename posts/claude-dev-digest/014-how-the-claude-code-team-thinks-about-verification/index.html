Claude를 여러 개 돌리려면 검증부터: Claude Code 팀의 테스트와 검사기 관리법

에이전트 한두 개를 돌릴 때는 결과를 사람이 하나씩 확인해도 버틸 만합니다. 동시에 돌리는 수가 늘면 확인하는 사람이 먼저 병목이 됩니다. 코드의 약 90%를 Claude가 쓰고 리뷰하는 Claude Code 팀은 검증 루프가 있어야 Claude를 수십, 수백 개씩 병렬로 돌릴 수 있다고 설명합니다.

한눈에 보기#

  • 먼저 투자할 테스트는 E2E, 속성, 차등 테스트이고 하나만 고르면 E2E입니다.
  • 팀은 커밋 전에 verify 스킬로 앱을 실제로 돌리고 세 라운드를 고쳐도 실패하는 검사는 사람에게 넘깁니다. 리뷰 규칙은 변경이 손댈 수 없는 base 브랜치에서 읽습니다.
  • 검사기도 과거 장애로 채점합니다. 놓친 버그는 규칙으로 바꾸고 쌓인 규칙은 주기적으로 정리합니다.

원문은 어떤 글인가#

Addy Osmani가 2026년 11월 16일에 쓴 글로 읽는 데 10분쯤 걸립니다. 같은 팀이 앞서 쓴 코드 리뷰 글(010번 글 참고)에서 검증 쪽으로 더 들어갑니다. 에이전트가 만든 변경을 사람이 다 읽지 못하는 팀의 개발 리드에게 맞습니다. 원문: How the Claude Code team thinks about verification

검증 수단이 위임할 수 있는 양을 정한다#

원문이 든 내부 실험에서는 구조화된 파일 생성 작업에 별도 채점기(grader)가 루브릭으로 결과를 확인하게 하자 작업 성공률이 일반 프롬프트 반복보다 최대 10포인트 올랐고 상승 폭은 가장 어려운 문제에서 가장 컸습니다. 테스트도 이제 에이전트가 금방 만들고 한번 만든 테스트는 자주 돌려도 토큰이 별로 들지 않습니다.

함정은 두 가지입니다. 들쭉날쭉한(flaky) 테스트는 에이전트에게 코드를 고치는 대신 테스트를 다시 돌리는 습관을 들입니다. 느린 테스트는 덜 돌리게 되니 문제 위치를 좁히기 어렵습니다.

먼저 투자할 테스트 세 가지#

E2E 테스트#

하나만 고르라면 원문은 E2E(end-to-end) 테스트를 꼽습니다. 상품을 장바구니에 담고 결제해 확인 페이지까지 가는 실제 사용자 흐름을 끝까지 돌리므로 속이기 어렵고 무엇이 깨졌는지 구체적으로 알려 줍니다. 아래 그림이 그 차이입니다.

그림 1. 왼쪽 UNIT TEST FAILURE(단위 테스트 실패)는 30초 타임아웃 메시지 하나뿐이라 어느 단계에서 막혔는지 알 수 없습니다. 오른쪽 END-TO-END TEST FAILURE(E2E 테스트 실패)는 TRACE(단계 기록), SCREENSHOT(화면), WHAT STEP FAILED(실패한 단계 설명)를 함께 내놓아 결제 폼이 뜨지 않아 Place order 버튼이 계속 비활성 상태였다는 것까지 알려 줍니다. 출처: 원문 .

단위 테스트는 빠르고 덜 흔들리지만 에이전트도 테스트도 전체 작업을 모르니 통과하고도 기능이 깨져 있을 수 있습니다. E2E에서는 앱을 띄워 조작하고 살펴보는 스킬을 만들어 CDP 나 시뮬레이터, API 하네스로 에이전트가 실제 시스템을 직접 보고 만지게 하면 효과적입니다. 사용자 관점의 경로, 단축키, 셀렉터와 기대 결과를 적은 기능 지도(feature map)는 안내서이자 채점 기준이 될 수 있습니다.

속성 테스트#

속성 테스트(property test)는 사람이 놓치기 쉽고 에이전트도 자주 실패하는 경계 사례를 노립니다. 깨지지 않는다고 믿는 성질을 적으면 fast-check(JS/TS), Hypothesis(Python), proptest(Rust) 같은 라이브러리가 입력 수천 개로 반박을 시도합니다. 원문이 드는 성질은 이렇습니다.

  • 왕복 변환: 인코딩했다가 디코딩하면 원래 값이 나옵니다.
  • 불변식: 계좌 잔액은 음수가 될 수 없다는 식의 늘 참인 조건입니다.
  • 멱등성: 마이그레이션, 정규화, 재시도를 두 번 해도 결과가 같습니다.
  • 동등성: 최적화한 코드와 단순하지만 정확한 코드가 같은 결과를 냅니다.

라이브러리가 만든 경계 사례는 코드를 쓴 에이전트와 편향을 공유하지 않습니다. 명세가 운영 동작과 어긋난 채로 코드를 다시 짤 때도 쓸모가 큽니다.

차등 테스트#

차등 테스트(differential test)는 기능이 그대로여야 하는 대규모 마이그레이션에 특히 잘 맞습니다. 옛 시스템을 정답지(oracle)로 삼아 두 시스템에 같은 입력을 넣습니다. 결과가 다르면 버그나 호환성을 깨는 변경이 있다는 뜻입니다. 입력은 무작위로 만들거나 운영 트래픽에서 뽑습니다. 공백 같은 무관한 차이는 정규화하고 일부러 달라진 부분은 승인된 변경 목록으로 관리합니다.

Claude Code 팀이 실제로 쓰는 규칙#

팀에게 검증은 곧 변경을 실행해 보는 일이고 테스트보다 앱을 끝까지 돌려 보는 쪽이 더 중요합니다. Claude는 웹이면 Claude Chrome 확장 , 모바일이면 iOS나 Android MCP, 데스크톱이면 computer use를 쓰고 백엔드는 서비스를 로컬에서 띄웁니다. 실행 방법은 verify 스킬에 적어 관련 코드 가까이의 .claude/skills/ 폴더에 두면 Claude가 커밋 전에 씁니다. 스모크 테스트 도구인 이 스킬도 Claude에게 개선과 스트레스 테스트를 맡겨 단단하게 다듬습니다.

  • 실패가 사람을 부른다: Claude가 고쳐 보다가 세 라운드 뒤에도 검사가 실패하면 멈추고 사람을 부릅니다. 검사는 코드 소유자가 쓰며 리뷰어를 부를 때는 이유도 적습니다.
  • diff로 켜지는 체크리스트: 신뢰성 점검 항목 39개마다 diff에서 읽을 수 있는 트리거, 확인할 내용, 근거가 된 장애나 PR이 붙어 있습니다. 세션 저장 방식이나 메시지 타입이 바뀌면 새 필드가 없는 옛 대화 기록도 --resume 으로 안전하게 불러오는지 묻는 식입니다. Claude는 트리거가 맞는 항목만, 보통 3개에서 10개를 확인합니다.
  • 리뷰어 하나, 라운드 여러 번: 비싼 리뷰어를 더 얹기보다 기존 리뷰어와 REVIEW.md를 손봅니다. 각 라운드는 앞 라운드의 맥락과 과거 실패를 이어받으니 처음부터 다시 보는 것보다 싸고 더 많이 찾습니다.
  • 규칙은 base 브랜치에서: 자기를 판정할 검사를 변경이 고칠 수 있다면 검사로서 의미가 없습니다. Code Review(Claude Code의 PR 리뷰 기능)는 REVIEW.md를 PR 변경분이 아니라 base 브랜치나 기본 브랜치에서 읽습니다. 리뷰도 커밋 단위로 겁니다. 원문 말대로 “오래된 커밋에서 통과한 리뷰는 아무 의미가 없습니다.”
  • 싼 검사부터: Claude는 PR을 열기 전에 테스트, 빌드, 린터를 돌립니다. 작업이 끝날 때 테스트를 돌리는 hook이나 테스트 통과를 목표로 건 /goal 로 강제할 수도 있습니다.

팀은 자기 저장소의 커밋마다 어떻게 검증했는지 표시하고 검증하지 않은 커밋에도 none을 남겨 쿼리로 찾습니다. 세션에서 /code-review 나 /verify 를 실행하지 않은 커밋을 막는 게이트에는 off, observe, enforce 세 모드가 있습니다. 원문이 글로만 설명한 동작을 흐름으로 옮기면 이렇습니다.

flowchart TD
  A["커밋 시도"] --> B{"/code-review나<br/>/verify를<br/>실행했나"}
  B -->|"예"| P["커밋 진행"]
  B -->|"아니오"| M{"게이트 모드"}
  M -->|"off"| P
  M -->|"observe"| L["막았을 커밋으로<br/>기록만 남김"]
  L --> P
  M -->|"enforce"| T{"이 세션에서<br/>이미 두 번 막혔나"}
  T -->|"예"| P
  T -->|"아니오"| X["커밋 차단"]

새 게이트는 observe 모드로 시작해 오탐이 없는지, 피해 보는 사람이 없는지 먼저 확인합니다. 커밋 메시지에는 검증하지 않은 이유를 적어 둘 수 있습니다. 한 세션에서 두 번 막힌 뒤 다음 커밋을 통과시키는 것은 Claude Code도 완벽하지 않아서 Claude가 갇히지 않게 하려는 장치입니다.

검사기를 검사하고 놓친 버그는 규칙으로#

팀은 리뷰어도 리뷰합니다. 되돌린 변경, 병합 전 메인테이너가 거절한 변경, 크기를 맞춰 고른 문제없는 변경 묶음을 추적합니다. Code Review 팀은 과거 장애와 되돌림 사례를 리뷰 당시 저장소 상태로 재현해 정식 평가를 돌리고 한 문장짜리 정답에 맞게 버그를 설명한 지적에만 점수를 줍니다. 안정적인 변경은 과잉 지적을 막는 대조군으로 넣고 튜닝용 세트는 평가 세트와 나눕니다. 재현율(recall)도 원본 지적, 검증 후, 최종 리뷰 단계마다 따로 재서 이미 찾은 버그를 중간에 잃는지 확인합니다. Claude Code 팀은 재현율을 평가 세트에 과적합하기 직전까지만 끌어올립니다.

Claude Code 저장소에서 놓친 사례를 규칙으로 바꾸는 길은 두 가지입니다. 하나는 사람의 리뷰 댓글과 되돌린 PR에서 반복 패턴을 뽑는 방법입니다. 두 PR 이상에서 나왔고 diff로 알아볼 수 있는 패턴만 후보가 되며 에이전트 세 개가 반박을 시도한 뒤 사람이 PR에서 승인합니다. 다른 하나는 알려진 장애와 연결된 PR에 버그 탐지기(bug finder) 세 개를 다시 돌리는 방법입니다. 둘 이상이 찾으면 탐지할 수 있는 버그이고 작은 diff에서 놓친 버그는 REVIEW.md 규칙으로 메울 만한 빈틈입니다.

들쭉날쭉한 테스트도 Claude가 건너뛰거나 sleep을 넣거나 통과할 때까지 재시도할 수 없습니다. 원인을 못 찾으면 테스트를 지우고 이유를 적습니다. 테스트와 검증 단계, .md 파일도 내버려 두면 늘기만 하니 주기적으로 정리합니다. 원문은 이렇게 하면 사람의 일이 diff를 다 읽는 데서 완료 기준을 정하고 증거를 검토하는 쪽으로 옮겨 간다고 맺습니다.

인사이트#

여기서부터는 원문이 아니라 이 블로그의 해석입니다.

  1. 데이터 파이프라인에는 차등 테스트가 그대로 들어맞습니다. 옛 ETL과 새 ETL에 같은 파티션을 넣고 결과 테이블을 대사(reconciliation)하는 일을 에이전트의 검증 단계로 두면 마이그레이션을 훨씬 많이 맡길 수 있다고 봅니다. 반올림이나 타임존 차이는 정규화와 승인 목록으로 다룹니다.

  2. 단계별 재현율은 NL2SQL이나 RAG 에이전트 평가에도 쓸 만합니다. 최종 정답률만으로는 검증 필터가 맞는 후보를 버리는지 알 수 없습니다. 검색, 후보 생성, 검증 필터 단계마다 정답이 남아 있는지 기록하면 고칠 곳이 바로 보입니다.

바로 해볼 것#

  • 앱을 띄워 핵심 사용자 흐름 하나를 끝까지 확인하는 verify 스킬을 .claude/skills/ 아래에 만들어 봅니다.
  • 자주 깨지는 함수 하나에 왕복 변환이나 멱등성을 확인하는 속성 테스트를 추가합니다.
  • CI가 쓰는 검증 규칙과 평가 데이터, 정답 쿼리를 PR이 고칠 수 있는지 확인합니다. 고칠 수 있다면 에이전트가 기대값이나 검증 SQL 조건을 느슨하게 바꿔 테스트를 통과시킬 수 있으니 base 브랜치에서 읽도록 바꿉니다.
