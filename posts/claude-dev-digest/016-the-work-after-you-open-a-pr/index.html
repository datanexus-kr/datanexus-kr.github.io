PR을 연 다음의 일은 Claude Code에 맡긴다: /ship, /steward, 승인 정책 설정 순서

11월 28, 2026 · 6 분 · Junho Lee

PR을 올리고 다음 작업으로 넘어가면 알림이 옵니다. CI가 실패했거나 리뷰 댓글이 여섯 개 달렸거나 main과 충돌이 났다는 소식입니다. 하나하나는 작은 일인데 그때마다 하던 일에서 빠져나와야 합니다. Claude Code 팀은 이 후속 작업을 대개 에이전트에게 맡기는데, 그 방식을 내 저장소에 들이는 순서대로 정리합니다.

한눈에 보기#

  • Claude Ship은 Code Review(정식 제공), PR Steward와 Claude Approvals(베타) 세 에이전트입니다.
  • 관리자 권한 없이도 /code-review, /ship, /steward 로 내 PR부터 시작할 수 있고, /ship 은 PR을 최대 7일 동안 지켜봅니다.
  • 반복되는 지적은 읽는 도구에 맞춰 CLAUDE.md, REVIEW.md, 스킬 파일 중 한 곳에 적습니다.
  • 팀 PR로 넓힐 때는 승인 정책을 observe 모드로 먼저 시험해 리뷰어의 판단과 비교한 뒤 강제합니다.

원문은 어떤 글인가#

Addy Osmani가 2026년 11월 24일에 쓴 글이고 읽는 데 16분쯤 걸립니다. Claude Code 팀의 코드 리뷰 와 검증 글에 이어 Claude Ship과 함께 나온 기능으로 내 저장소를 설정하는 법을 다룹니다. GitHub를 쓰지만 관리자 권한은 없는 개발자나 테크 리드에게 맞습니다. 원문: A practical guide to shipping with Claude Code

PR 다음에 오는 세 가지 일#

원문은 PR 이후의 일을 문제 찾기, 문제 고치기, 병합 여부 결정으로 나눕니다. 앞의 둘은 지금도 일부 자동화할 수 있고, 마지막 결정은 브랜치 보호 규칙과 (팀이 쓴다면) 정책 파일에 정해 둡니다.

하고 싶은 일실행실행 위치
남이 보기 전에 버그 찾기/code-review내 세션
PR 열기부터 피드백 처리까지/ship내 세션
이미 연 PR 돌보기/steward내 세션
팀 PR 전체 자동화Claude Ship기본은 Anthropic 클라우드, 팀이 설정

내 PR에서 시작하기#

하나만 해 본다면 푸시 전 /code-review 부터 돌리라고 원문은 권합니다. 브랜치의 커밋과 커밋 전 변경에서 정확성 버그를 찾습니다. effort를 low에서 max로 올릴수록 확신이 낮은 지적까지 보여 주고, 클라우드에서 도는 ultra 는 요금제와 따로 청구될 수 있습니다.

PR이 아직 없는 브랜치에서 /ship 을 실행하면 아래처럼 움직입니다.

flowchart TD
  A["ship 명령 실행"] --> B["대기 중인 변경 커밋<br/>git add -A처럼 동작"]
  B --> C["푸시하고<br/>내 계정으로 PR 생성"]
  C --> D["code-review 후<br/>타당한 지적 수정"]
  D --> E["최대 7일 감시<br/>검사 실패, 충돌, 댓글"]
  E -->|"병합 또는 닫힘"| F["감시 종료"]
  E -->|"재설계, 못 푼 보안<br/>문제 같은 큰 판단"| G["작성자에게 넘김"]
  E -->|"같은 문제에<br/>푸시 3회"| H["시도한 해법 보고"]
  H --> G

첫 커밋이 git add -A 처럼 동작하니 실행 전에 git status 를 봅니다. /ship 은 이름이 비밀 값처럼 보이는 파일과 CLAUDE.md, REVIEW.md, .claude/, .github/ 같은 규칙 파일은 커밋하지 않으니, 이런 변경은 직접 커밋해야 합니다. 감시는 내 컴퓨터에서 내 계정과 사용량으로 돌아 노트북을 닫으면 멈춥니다. 브랜치도 체크아웃한 채 둬야 하니 다음 작업은 별도 worktree에서 합니다.

감시는 필요하면 base 브랜치를 병합하고 테스트 같은 명령을 돌리므로, base 브랜치에 변경을 넣을 수 있는 사람은 누구나 내 컴퓨터에서 명령을 돌릴 수 있습니다. Claude Code가 무인 턴의 직접 병합과 강제 푸시를 막아도 테스트 스크립트는 내 자격 증명으로 돌고, 감시의 커밋은 git hook을 거치지 않습니다. 그 사람들을 모두 믿는 저장소에서만 감시를 돌리고, 꼭 필요한 검사는 CI와 브랜치 규칙에 둡니다.

이미 연 PR에는 /steward 41 처럼 리뷰를 건너뛰고 감시만 돌립니다. 검사가 실패했거나 충돌이 되풀이되는 PR에 맞고, 설계 논쟁 중인 PR은 내가 결론 낼 일이라 맞지 않습니다.

반복되는 지적은 규칙 파일로#

PR이 쌓이면 같은 리뷰어의 같은 지적, Claude가 매번 헤매는 실행 방법, 불안정한 검사가 보입니다. 원문은 이를 읽는 도구에 맞춰 나눠 적으라고 합니다.

반복되는 것적을 곳읽는 도구
코드가 따라야 할 관례CLAUDE.mdClaude Code, 로컬 /code-review, Code Review, PR Steward
PR 리뷰 규칙REVIEW.mdCode Review, PR Steward (로컬 /code-review 제외)
앱을 띄워 확인하는 법.claude/skills/verify/SKILL.md변경을 검증하는 Claude Code
PR 관리 방식.claude/skills/steward/SKILL.md/ship, /steward, PR Steward

새 쿼리에 테넌트 확인을 넣으라는 지적을 두 번 받았다면, 로컬 리뷰만 쓸 때는 CLAUDE.md에, Code Review를 쓴다면 REVIEW.md에 적습니다. 원문 예시의 REVIEW.md는 틀린 결과, 데이터 유출, 롤백을 막는 문제를 Important로 정하고 Nit은 다섯 개까지만 보고하게 합니다. Claude Code 팀은 PR 두 개 이상에서 반복된 패턴만 규칙 후보로 삼고, 규칙을 넣는 PR은 사람이 승인합니다. verify 스킬은 Claude에게 몇 번 돌려 보게 하고 불안정한 부분을 고칩니다. 원문 말대로 “믿지 못하는 검증은 사람들이 무시합니다”.

팀 PR로 넓히기: observe 모드부터#

여기부터는 관리자에게 요청할 일입니다. 저장소 하나와 자원자 몇 명, 기한을 정한 시험 기간을 받고 예산 한도를 미리 합의합니다. 기본 브랜치를 보호하고 Claude 조직의 Owner가 Code Review와 PR Steward(Manual 모드)를 켭니다.

승인 정책은 기본 브랜치의 .claude/approvals.yml 에 둡니다. 이 파일을 병합하면 Approvals가 켜지니 Owner와 먼저 상의합니다. 원문의 첫 정책은 observe 모드에서 모든 경로에 두 사람 승인을 요구하고, 규칙 파일에는 같은 기준을 하나 더 걸어 nested: inherit 로 하위 디렉터리 정책에도 물려줍니다. 첫 규칙에서 눈여겨볼 두 줄은 이렇습니다.

verdict: { claude: comments, seats: 2 }
advisory: [claude/code_review]

seats 는 승인할 사람 수이고 작성자도 한 자리를 채울 수 있습니다. claude: comments 면 Claude는 승인하지 않고, 여러 규칙이 맞으면 가장 엄격한 규칙을 따릅니다. advisory 줄을 지우면 자동 리뷰가 멈춥니다. 정책 파일이 올라간 뒤로는 Code Review가 자신을 지정한 규칙에 맞는 PR에서만 돌기 때문입니다. advisory를 override 로 바꾸면 Code Review를 통과한 PR의 기준이 사람 한 자리와 Claude 승인으로 낮아집니다. 다만 PR 안의 텍스트에 리뷰가 흔들려 통과하면 그 PR도 낮아진 기준을 적용받습니다. 이런 정책은 observe 모드에서도 푸시마다 리뷰 비용을 청구할 수 있으니 병합 전에 예산 담당자에게 알립니다.

observe 모드에서는 판단만 기록되고 Claude는 아무것도 승인하지 않습니다. 한두 주 뒤 병합된 PR을 다시 보며 그 판단과 리뷰어의 실제 행동을 맞춰 봅니다.

정책의 판단리뷰어의 실제 행동할 일
승인했을 것그대로 승인규칙 유지
승인했을 것수정 요청사람이 필요한 경로 규칙 추가나 REVIEW.md 수정
두 사람 필요매번 훑어보고 승인사례가 쌓이면 범위 축소 검토
두 사람 필요실제 질문이 나옴규칙 유지

위의 두 행은 override를 넣은 뒤에야 나오고, 규칙을 완화하기 전에 두 번째 행부터 고칩니다. Claude의 승인은 GitHub에서 실제 승인으로 계산되므로 승인 하나만 요구하는 브랜치 규칙은 Claude 혼자 채울 수 있습니다. auto-merge를 켠 저장소에 위의 override처럼 작성자 혼자 채울 수 있는 정책이 있으면 아무도 손대지 않은 PR이 병합될 수도 있으니, 경로마다 허용할지 정해 적어 두라고 원문은 권합니다. 그래서 정책과 브랜치 규칙을 함께 읽고 아래 순서로 잠급니다.

flowchart LR
  A["사람 필수 경로를<br/>if, override 없는 규칙으로"] --> B["mode: observe<br/>지우고 병합"]
  B --> C["5분쯤 뒤 열린 PR에<br/>@claude approvals rerun"]
  C --> D["Approvals 체크를<br/>필수로 지정"]
  classDef human fill:#fde8e0,stroke:#d97757,color:#3a2a22
  class A human

마지막 단계 전까지는 체크 결과와 상관없이 PR이 병합될 수 있습니다. Claude Ship도 버그나 보안 문제를 놓칠 수 있으니 기존 테스트와 스캐너, 리뷰어는 그대로 둡니다. Claude Code 팀에서는 에이전트를 부른 사람이 그 변경을 직접 입력한 것처럼 책임집니다.

인사이트#

여기서부터는 원문이 아니라 이 블로그의 해석입니다.

  1. 로컬 감시의 보안 경계는 base 브랜치에 코드를 넣을 수 있는 사람 전체로 넓어집니다. 데이터 파이프라인 저장소는 테스트가 웨어하우스 자격 증명으로 실제 쿼리를 돌리기도 하니, 감시를 켜기 전에 테스트가 어디에 접속하는지부터 봐 둘 만합니다.

  2. observe 모드와 네 줄짜리 비교표는 에이전트에게 쓰기 권한을 주기 전의 섀도 운영과 같습니다. 사내 에이전트도 판단을 기록만 하며 사람의 결정과 맞춰 보면, 에이전트는 통과시켰는데 사람은 막은 사례가 먼저 드러납니다.

바로 해볼 것#

  • 현재 브랜치에서 /code-review 를 돌려 틀린 지적과 놓친 버그를 적어 둡니다.
  • 병합 권한자를 모두 믿는 저장소에서 다음 PR에 /ship 을 돌리고 첫 감시 동안 자리를 지키며 사용량을 봅니다.
  • 가장 자주 받은 리뷰 지적을 CLAUDE.md나 REVIEW.md에 적는 작은 PR을 직접 커밋합니다.
