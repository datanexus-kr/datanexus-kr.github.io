출시 전 2주 동안 Claude가 스테이징을 부수고 고쳤다: Claude Docs의 카오스 루프

11월 28, 2026 · 5 분 · Junho Lee
목차
  • 한눈에 보기
  • 원문은 어떤 글인가
  • 카오스 루프는 이렇게 돌았다
  • Claude가 원인을 따라갈 수 있는 서비스
  • 출시 결과와 비용
  • 인사이트
  • 바로 해볼 것

서비스가 출시 트래픽을 버틸지는 사내 사용자만으로 알 수 없습니다. Claude Docs 팀은 출시 전 2주 동안 Claude에게 스테이징을 쉬지 않고 부수고 고치게 해서 답을 찾았습니다.

한눈에 보기#

  • 2026년 9월 16일 출시 후 9월 22일까지 사용자가 만든 문서가 460만 개를 넘었습니다. 요청 20억 건에서 서버 오류는 60건이었고 롤백은 한 번도 없었습니다.
  • Claude Code 세션 하나가 2주 동안 부하 테스트부터 스테이징 배포까지 반복했고, 사람은 되돌리기 어려운 변경만 승인했습니다.
  • Claude가 숫자에서 원인 코드까지 따라갈 수 있게 가비지 컬렉터가 없는 Rust로 서비스를 쓰고 의존성을 최소로 줄였습니다.
  • 8월 말부터 출시일까지 쓴 추론은 Claude Fable 5.2 API 정가(2026년 11월 기준)로 약 125,000달러어치입니다. 저자는 작은 서비스라면 2주에 3,000달러에서 10,000달러로 추정하지만 직접 돌려 보지는 않았습니다.

원문은 어떤 글인가#

Vivek Nair가 2026년 11월 17일에 쓴 글이고 읽는 데 9분쯤 걸립니다. Claude Docs는 사람과 Claude가 한 문서를 함께 편집하는 도구이고, 원문은 그 밑에서 도는 서비스를 출시 규모로 키운 과정을 다룹니다. 출시를 앞두고 부하 테스트를 에이전트에게 맡겨 보려는 백엔드 개발자에게 맞습니다. 원문: Using a “chaos loop” to harden the Claude Docs launch

카오스 루프는 이렇게 돌았다#

출시 3주 전 Claude Docs는 노드 한 대에서 사내 몇천 명이 쓰는 개념 검증 버전이었습니다. 출시 며칠 만에 문서가 수백만 개 생길 것으로 본 저자는 9월 4일부터 운영 환경을 본뜬 스테이징 클러스터를 Claude에게 맡겼습니다. Claude는 하루 100만 개가 넘는 합성 문서를 밀어 넣으며 핵심 컴포넌트를 일부러 망가뜨렸습니다. 시나리오는 저자가 스스로도 과하다 싶을 만큼 골랐습니다. 하루 새 문서 1,000만 개, 연결 22,000개의 동시 재접속, 수백 명이 보는 인기 문서, 문서를 불러오던 중 죽는 서버, 멈춘 데이터베이스 같은 경우입니다.

루프를 돌린 Claude Code 세션은 조정자를 맡아 작업 대부분을 서브에이전트에게 넘겼는데, 가장 바쁜 주에는 보통 11개쯤, 많을 때는 30개까지 동시에 돌았습니다. 하네스(부하를 걸고 결과를 재는 테스트 장치)가 문서 생성 같은 기능을 포화 상태까지 몰아붙이면, Claude가 Datadog MCP로 텔레메트리를 읽고 선택지 몇 개와 추천안을 내놓았습니다. 쿼리마다 이름과 스캔한 행 수, 반환한 행 수가 남아 있어서 Claude는 비효율적인 쿼리를 찾아 다시 쓸 수 있었습니다.

아래 그림이 반복 한 번입니다.

그림 1. 파란 점은 Claude가, 주황 점은 사람이 하는 단계입니다. 위 줄은 부하 걸기(Harness adds load)부터 사람의 선택까지, 아래 줄은 변경 작성부터 별도 세션의 리뷰, 사람의 승인, 스테이징 배포까지입니다. 가운데 문구는 두 불변 조건입니다. 출처: 원문 .

그림에서는 사람이 반복마다 두 번 결정하지만, 본문을 보면 되돌리기 쉬운 변경은 Claude가 직접 스테이징에 배포하고 테스트를 다시 돌렸습니다. 데이터베이스 스키마나 키 구성, 문서 저장 방식처럼 되돌리기 어려운 결정에서만 멈춰 추천안과 함께 물었고, 저자는 대개 그 추천을 승인했습니다. 테스트 내내 지킬 불변 조건도 두 개 줬습니다. 이력이 긴 문서도 거의 바로 열려야 하고, 서버가 받았다고 확인한 편집은 테스트에서도 남아 있어야 합니다.

Claude가 원인을 따라갈 수 있는 서비스#

저자의 동료 Felix Rieseberg는 튜토리얼 에서 충돌 하나하나를 고치게 하지 말고 충돌 없는 앱이라는 결과를 요청하라고 권합니다. 그러려면 Claude가 증상을 스스로 읽고 수정을 확인할 수 있어야 해서 Docs 팀은 두 가지를 했습니다.

하나는 Claude가 반복마다 텔레메트리를 읽고 빠졌다고 본 계측을 채우게 한 것입니다. 파드에서 약 3GB를 쓰던 큰 문서가 좋은 예입니다. Claude는 캐시 하나를 줄여 봤다가, 다음 실행에서 메모리가 의존성 라이브러리 안의 다른 캐시에 있다는 게 드러나자 변경을 철회했습니다. 더 세밀하게 프로파일링한 끝에 키 입력마다 문서가 여러 자료구조로 복사돼 몇 MB씩 늘어나는 원인을 찾아 이 구조들을 copy-on-write로 바꿨습니다. 약 3일을 반복한 뒤 그 문서는 최대 약 180MB에 그쳤고, 출시에 필요하다고 본 메모리 최적화 파드도 500개 이상에서 약 50개로 줄었습니다.

다른 하나는 기술 선택입니다. 모델은 신호가 깨끗할수록 점수를 올려 가며 개선(hill climb)하기 쉬운데, 팀은 가비지 컬렉터가 있으면 메모리와 지연 시간이 수집 일정에 따라 흔들려 잡음이 생길 것으로 봤습니다. 그래서 서비스를 Rust로 쓰고 의존성은 최소한만 두되, 꼭 필요한 라이브러리는 코드를 저장소에 들여와(vendoring) 읽고 잴 수 있게 했습니다.

그림 2. 위 줄(What we chose)은 Rust와 적은 의존성이 확인하기 쉬운 수정으로, 아래 점선 줄(What we avoided)은 가비지 컬렉션과 남이 쓴 라이브러리가 잡음 많은 신호로 이어지는 흐름입니다. 출처: 원문 .

팀은 두 언어를 맞대어 비교하지 않았고 사내 Go 도구도 잘 갖춰져 있다고 밝힙니다. 그림 아래 줄에 “a bet, not a test”라고 적은 것도 그래서입니다. 사람이 쓰기 어렵다는 Rust의 약점은 Claude가 Rust를 무리 없이 쓰는 지금은 훨씬 덜 중요하다고 덧붙입니다.

출시 결과와 비용#

첫 문서 100만 개가 약 30시간 만에 쌓였고, 9월 한 달 운영 배포 629번 가운데 롤백은 한 번도 없었습니다. 스테이징에서 연습한 시나리오 열 개 중 일곱 개가 실제로 일어났지만, Claude가 수정을 이미 런타임 플래그 뒤에 넣어 둬서 대개 플래그만 바꾸면 됐습니다. 저자는 몇 달 전 모델이었다면 열 번, 스무 번 반복하는 사이 목표를 잊는 현상(goal drift) 때문에 아마 안 통했을 거라고 봅니다. 이번에 쓴 사내 연구 모델은 Claude Fable 5.2와 대략 비슷한 수준으로, 컴팩션(긴 컨텍스트를 요약해 줄이는 처리)을 여러 번 거치고도 불변 조건을 놓치지 않아 다시 알려 줄 필요가 없었습니다.

Claude Fable 5.2 API 정가로 약 125,000달러어치 추론이 든 이 작업을 저자는 2년쯤 전이라면 엔지니어 팀이 6개월쯤 걸렸을 규모로 짐작합니다. 방법을 찾느라 태운 토큰이 많아서 지금 아는 걸 처음부터 알았다면 절반 정도면 됐을 거라고도 봅니다. 쿠버네티스 노드 두어 대와 Postgres 인스턴스 하나로 된 작은 서비스라면 필요한 변경이 약 3분의 1만 남고, 시행착오까지 빼면 같은 정가로 2주에 3,000달러에서 10,000달러쯤 들 것으로 추정하는데, 직접 돌려 본 수치는 아닙니다.

인사이트#

여기서부터는 원문이 아니라 이 블로그의 해석입니다.

  1. 되돌리기 어려운지를 사람 승인 기준으로 삼은 방식은 그대로 가져다 쓸 만합니다. 데이터 파이프라인이라면 스키마, 파티션 키, 저장 포맷 변경은 사람이 고르고, 다음 실행에서 되돌릴 수 있는 쿼리 재작성은 에이전트에게 맡기면 됩니다.

  2. Claude가 비효율 쿼리를 찾아낸 근거인 쿼리별 스캔 행 수와 반환 행 수는 데이터 팀에게 익숙한 지표입니다. 에이전트 시스템도 도구 호출마다 지연 시간과 토큰 수를 남겨 두면 같은 방식으로 원인을 좁힐 수 있을 것 같습니다.

  3. 두 불변 조건 중 하나는 테스트로 확인하는 조건이었습니다. 몇 주씩 도는 에이전트 작업이라면 지킬 조건을 지시문에만 두지 말고 테스트로 바꿔 두는 편이 안전해 보입니다.

바로 해볼 것#

  • 스테이징의 쿼리 로그에 쿼리 이름과 스캔 행 수, 반환 행 수가 함께 남는지 확인합니다.
  • 서비스가 꼭 지켜야 할 불변 조건을 두세 개 적고, 각각을 확인하는 테스트가 있는지 봅니다.
  • 에이전트 지시 파일에 되돌리기 어려운 변경 목록을 적고, 그 앞에서는 멈춰 추천안을 먼저 내라는 규칙을 넣습니다.
