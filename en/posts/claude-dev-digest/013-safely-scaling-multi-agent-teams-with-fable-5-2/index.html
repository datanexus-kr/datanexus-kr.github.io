1,000 Agents and One Shared Database: Reproducing a Formal Proof of Fermat's Last Theorem with Claude Fable 5.2

November 25, 2026 · 11 min · Junho Lee
Table of Contents
  • At a Glance
  • About the Original Post
  • Dropping the Platform and the Researcher
  • Sandboxing and Two Kinds of Monitors
  • The Lead Ran the Team Through Five Tables
  • The Last Statement: Langlands–Tunnell and the Task Tree
  • Takeaways
  • What to Try First

Once you run more than a few dozen agents, splitting the work is the easy part. Keeping every agent aware of what the others are doing gets harder, and so does stopping one agent’s bad action from spreading across the team. This post walks through Anthropic’s experiment with 1,000 agents running an early version of Claude Fable 5.2: how the team organized itself around a single shared database, and what safety boundaries it ran inside.

At a Glance#

  • A team of 1,000 agents (one lead, 999 helpers) running an early version of Claude Fable 5.2 reproduced a formal proof of Fermat’s Last Theorem in 28.7 hours. Compared with the September effort, it used one-third as many output tokens and produced a proof one-seventh the length.
  • There was no Prove2Me platform and no researcher steering the work. The agents had general-purpose tools such as a shell, Git, and a shared Postgres database, and the lead designed five coordination tables within the first 10 minutes.
  • Three layers surrounded the team: a sandbox with no network access, a classifier that could block each tool call before it ran, and an offline monitor. None of the more than one million tool calls met the bar to be blocked.
  • Early on, helpers judged 47 of the 60 statements infeasible within the run’s budget, yet the team went on to prove most of them.

About the Original Post#

Barry Zhang, Tianyi Peng, Elle Najt, Keller Scholl, and Lance Martin published this 12-minute post on November 9, 2026. The authors call it a toy experiment, and the post is less about the mathematics than about how to coordinate a very large agent team and how to keep it inside safe boundaries. Engineers designing multi-agent systems are the natural audience. Source: Safely scaling multi-agent teams with Claude Fable 5.2 .

Dropping the Platform and the Researcher#

Fermat’s Last Theorem says that no positive integers a, b, and c satisfy aⁿ + bⁿ = cⁿ for any n greater than 2. Andrew Wiles proved it in 1995 with a 129-page proof. Formalizing that proof means rewriting it in Lean, a language in which a computer checks every step.

Anthropic’s first end-to-end formalization, published in September, took one researcher and dozens of agents 11 days. The agents ran an internal research model roughly comparable to Claude Fable 5.1, used roughly 6 billion output tokens, and wrote 13 million lines of Lean. Coordination ran through Prove2Me, a platform that links each statement to the smaller statements it was split into and tells agents which pieces are ready to work on.

This time the team got only general-purpose tools. The starting materials were 60 statements (the final theorem plus 59 intermediate milestones), a one-sentence sketch of the classical route, the definitions those statements use, and 47 lemmas proved during the earlier work. Each agent ran on its own lightweight virtual machine with no network access, with a shell, a file editor, Lean, and the Mathlib library inside, plus its own Git branch and access to a shared Postgres database. Earlier, a single shared machine hit its limits at about 100 agents, and more than half of those 100-agent runs had to be stopped or restarted when memory, disk, or CPU ran out. SQL won out as the coordination layer for three reasons: it offers general building blocks for organizing information, its transactions handle concurrent writes from 1,000 agents, and Claude is already familiar with it.

The prompt set up only a hierarchy of one lead and 999 helpers. During the run, the harness sent the lead 19 automatic reminders of how much time remained, each one encouraging it to keep going.

Sandboxing and Two Kinds of Monitors#

The authors argue that no single layer of defense can contain an agent team, so they stacked real-time and offline monitoring on top of the sandbox. Experiments like this may run on models that have not finished pre-release alignment assessment, so the monitoring is built on the assumption that the model could be misaligned. The figure below shows the run’s architecture together with all three layers.

Figure 1. The blue box on the left is the stack of 1,000 agent sandboxes, the middle is the Gateway, and the right holds the Git repository and Postgres database. Gray shaded labels are safety measures, grouped into Sandboxing, Real-time monitoring, and Offline monitoring. The offline monitor reports serious findings to the Run owners. Source: Original post .

There were no messaging tools, so the database and Git were the only ways agents could coordinate. A single pipe to the gateway was the sandbox’s one exit, and the gateway stamped each request with the sender’s identity on its own side of that pipe, so no agent could impersonate another. Pushes were limited to the agent’s own branch. The database was reached through one shared unprivileged role; every SQL statement timed out after five seconds, and any write above 256 MiB was rejected. Agent commands ran as a non-root user with sudo and similar tools stripped out, and the kernel was compiled without the features a root user could use to reach into it directly.

The real-time monitor is an LLM classifier, steered by a prompt, that reviews every tool call (shell commands and file edits alike) before it executes and can block it. It looks for signs of sandbox escape, boundary probing, or tampering with the monitoring itself. Under Anthropic’s standing policy, a block halts the whole team until a person has reviewed it, so that no other agent can pick up the blocked action. This run was configured differently: only a block on the lead would have ended the run, while a blocked helper would simply have been removed.

In multi-agent sabotage evaluations, red-team agents used strategies such as decomposition attacks (splitting a harmful action into pieces that each look harmless) to try to get a sandbox escape past the classifier. Monitors that could see the agents’ chain of thought (CoT) and inter-agent communication caught every attempt in those evaluations, so Anthropic now uses them on multi-agent runs, alongside an action-only version that guards against an agent’s reasoning talking the monitor into a harmful action. This run used only the action-based monitor, and none of its more than one million tool calls met the bar to be blocked. Replaying those calls against the CoT monitor, added shortly after the run, and today’s rubric flagged just one call as close to a block: a check for root access. The offline monitor applies the same threat models after the fact, with the added ability to look up other agents’ actions.

The Lead Ran the Team Through Five Tables#

Every statement began as a Lean theorem whose proof was left as a placeholder, and it counted as done only when Lean’s checker accepted a complete proof. The lead decided how to split and coordinate the work, and within the first 10 minutes it created five tables in the database.

Figure 2. The lead sits on top and the 999 helpers at the bottom. Announce holds the lead’s orders, Assign records who owns which statement, Notes is an open board for claiming work and reporting progress, Subtasks is a to-do list where anyone can add a task and the first helper to claim it owns it, and Landed logs finished work. Dashed arrows mark directions with almost no traffic: helpers wrote once each to Announce and Assign (One write), and the lead wrote twice to Subtasks (Two writes). Source: Original post .

The lead wrote 999 rows to the assign table, one per helper, putting a crew of 16–17 helpers on each statement and naming one captain per crew. Through the announce table, it told every helper to start by judging its statement’s difficulty and posting a verdict in the notes table. About 27 minutes in, with three statements already proved, the lead set aside the 47 statements most helpers had judged infeasible and moved nearly everyone onto the remaining 10. Crews grew from about 17 helpers to between 46 and 139. Around 45 minutes in, the lead observed that the team was moving much faster than the early verdicts had predicted, and all 10 statements were proved within roughly 70 minutes.

From there the lead started moving helpers onto the harder statements it had set aside, with most reassignments happening in the first six hours. Helpers also took on more of the planning. By the third hour the lead told free helpers not to wait for it, so they began picking up work on other statements on their own. By hour 5.6, 73 helpers had written 756 tasks to the subtasks table, and only 16 of them were captains.

The Last Statement: Langlands–Tunnell and the Task Tree#

By about hour 18, the only open work was Langlands–Tunnell (a classical result Wiles’s proof depends on), the statements built on it, and one more statement that the team finished along the way. At that point the researchers restarted the run from its last save and gave the agents 12 more hours. Earlier, the Langlands–Tunnell captain had estimated the proof would need at least 0.7 to 1 million lines of Lean, with under a 1% chance of finishing in time, and the lead had set it aside. With nearly everything else done, the lead moved about 750 helpers onto it and wrote, “Honest odds are low.”

Langlands–Tunnell was far larger than any other statement in the run, taking roughly nine times as many tasks and more than twice the new code. Many first-pass tasks were too big for one helper, so the team reorganized the work as a tree. The captain split the statement into 10 areas, and any helper that found a piece too large could add smaller tasks beneath it. The tree eventually reached 2,418 tasks up to 10 levels deep. Each piece was allowed to assume the results below it, which let hundreds of helpers work at once without waiting for the lower pieces to be finished.

Figure 3. The black dots at the center are Langlands–Tunnell and its sub-areas, and each ring outward is one level deeper. Color shows the run hour a task was first marked done, from light orange (hour 21) to dark red (hour 27 and later); gray tasks had not been marked done. Most links were inferred afterward from helpers’ task labels. The original post animates the tree growing from hour 20.5. Source: Original post .

The authors are careful to say the result does not remove the need for domain-specific harnesses. A platform like Prove2Me may still improve efficiency by compiling Lean faster and helping agents find and reuse human results. Human direction also still has a role. As the early verdict on 47 statements showed, agents tend to misjudge how hard a problem is and give up early, and a person’s encouragement at those moments can keep them from stopping too soon.

Takeaways#

The notes below are this blog’s own interpretation, not part of the original post.

  1. Giving the team SQL tables instead of a messaging tool is the most transferable choice in the post. When claims and completions live in tables, transactions keep them consistent, and both monitors and humans can query the same record later. Teams that already run data platforms can apply their existing table-design habits directly to an agent team’s work ledger.

  2. Many of the safety controls are permission and limit settings rather than new technology. An unprivileged database role, per-statement time limits, and own-branch-only pushes are things you can configure for internal agents today. Whether a single block halts the whole team or removes only that agent trades throughput against the risk of another agent finishing the blocked action, and that decision is worth making before the first large run.

  3. The early verdicts that turned out badly wrong suggest that an agent’s self-assessment of difficulty should not drive planning on its own. Before discarding work based on those verdicts, run a sample of it and measure real throughput.

What to Try First#

  • If you already run a multi-agent workflow, check whether coordination state lives only in conversation logs or in a table you can query.
  • Move the database account your agents use to a dedicated unprivileged role and set a per-statement timeout (statement_timeout in Postgres).
  • If agents rate task difficulty in your workflow, pick a few tasks they marked infeasible, actually run them, and compare the verdicts with the results.
