Claude Code Cloud Sessions: Running Parallel Tasks Beyond Your Laptop

October 14, 2026 · 9 min · Junho Lee
Table of Contents

  • About the Original Post
  • Three Tasks on Three Machines at Once
  • Anatomy of a Cloud Session
  • Workloads That Fit the Cloud
  • GitHub Permissions and Environment Setup
  • Takeaways

A Claude Code session running in your laptop terminal inherits every constraint of that laptop. Opening two sessions in the same repository means sharing one working directory, where concurrent edits and local server ports collide. Every session runs with your full local user permissions, and closing the lid or losing Wi-Fi stops the work mid-turn. Cloud sessions remove all three constraints by moving each task into an isolated virtual machine. This post breaks down how cloud sessions are structured and which tasks belong in the cloud versus on your laptop.

At a Glance#

  • Every cloud session boots a fresh virtual machine (VM), clones your repository onto a new branch, and leaves its changes on that branch ready to open as a pull request.
  • Cloud sessions are included at no extra machine charge on Pro, Max, Team, and Enterprise plans, drawing from your existing Claude Code usage allowance.
  • Because sessions share neither files nor ports, they fit parallel bug fixes and verification loops that run a test suite dozens of times in a row.
  • GitHub permissions cause most first-run failures: signing in with GitHub and installing the Claude GitHub App are two separate steps.

About the Original Post#

Addy Osmani published this 18-minute field guide on October 6, 2026. Rather than staying abstract, the post runs four real cloud sessions against a small sample repository and shares the actual transcripts, diffs, and wall-clock timings. It is written for developers who already use Claude Code in a local terminal and want to know when to offload work to the cloud. Source: Claude Code in the cloud .

Three Tasks on Three Machines at Once#

The sample repository, tidepool, is a small Node API that predicts tides across three fictional harbors. It has three separate issues: a test that fails roughly one run in four, API documentation that has drifted from the implementation, and plain string-concatenated logs. The author launches three cloud sessions within 16 seconds, assigning one task to each.

Figure 1. Horizontal axis shows seconds elapsed since launching the first session. Hatched bars mark demo repository setup, where a standard GitHub clone normally happens; each dot represents one tool call. Source: Original post .

Each session ran for 61 to 72 seconds, and all three wrapped up within 87 seconds of the first launch:

  • Flaky test: Claude traced the failure to a race condition in TtlCache.get, where a second request for the same key arriving mid-fetch triggered a duplicate loader call. It cached the in-flight promise and ran npm test 40 times in a row with zero failures.
  • API docs: Claude started the server, queried every endpoint with curl, and fixed five mismatches between the responses and the documentation.
  • Structured logs: Claude replaced string logs with JSON output and added five tests. When one test failed during verification, Claude traced it to the same cache race condition VM 1 was fixing, left the out-of-scope cache code untouched, and noted the dirty test run in its summary.

Because each session had its own repository clone, process space, and branch, the documentation and logging sessions could both boot the API server simultaneously without port conflicts. Isolation has a flip side: the logging session could not see the cache fix happening next door. When splitting parallel work, cut along clean file boundaries and expect adjacent sessions to flag pre-existing bugs that another session is already fixing.

Anatomy of a Cloud Session#

Inside each session, the VM sits inside a strict boundary while credentials and network controls stay outside it.

Figure 2. Left (START OR CHECK FROM) shows where sessions can be launched—and monitored from browser, mobile, or desktop. Center (FRESH VM PER SESSION) shows the isolated VM, while right (OUTSIDE THE VM) shows the proxies handling credentials and network policy. Source: Original post .

Four architectural choices shape day-to-day usage:

ComponentHow cloud sessions handle it
MachineA fresh VM per task; sessions never share files, processes, or ports
GitHub tokenNever enters the VM; a proxy issues a short-lived credential scoped to push only to that session’s working branch
ConfigurationRepository CLAUDE.md, rules, and skills travel with the clone, while your personal ~/.claude stays on your laptop
Idle VMsReclaimed after inactivity; reopening restores the conversation in a new VM, so uncommitted file edits do not survive

Cloud sessions do not replace local sessions. Tasks that depend on local-only resources—a local database with test data, internal services behind a VPN, a GPU, or a mobile simulator—still belong on your laptop, as does rapid UI iteration where you check a local browser every few seconds. Organizations under Zero Data Retention policies also stay local-only because cloud sessions are disabled there.

Workloads That Fit the Cloud#

From the seven workflows in the original guide, four stand out for everyday engineering work:

  • Firing off parallel small fixes: Run claude --cloud "task description" once per task. Because cloud sessions clone the current branch from GitHub remote, push your local commits first. Write each prompt with three specifics: what is broken, what done looks like, and which command proves it.
  • Demanding proof of a fix: Because the cloud VM burns remote compute rather than your laptop CPU, you can ask for thorough verification—such as running the full test suite 40 times in a single loop to confirm a race condition is gone.

Figure 3. The runs=40 fails=0 output at the bottom confirms 40 consecutive clean runs, followed by Claude’s root-cause writeup. Source: Original post .

Foreground bash commands time out after 2 minutes by default (up to 10 minutes max) and can continue running in the background for up to 30 minutes. You can raise those defaults via BASH_DEFAULT_TIMEOUT_MS and BASH_MAX_TIMEOUT_MS.

  • Planning locally, executing in the cloud: For larger changes, align on an implementation plan interactively on your laptop first, hand execution off to a cloud VM, and pull the finished branch back down when needed.
flowchart LR
  A["Local plan mode<br/>Align on plan"] -->|"Commit and push"| B["claude --cloud<br/>Execute plan"]
  B -->|"Push branch"| C["claude --teleport<br/>Pull into terminal"]
  C --> D["Finish by hand"]

Running claude --teleport brings both the cloud session’s Git branch and its conversation history into your local terminal. The branch must already be pushed, and your local working tree should be clean—if uncommitted changes exist, Claude Code offers to stash them.

  • Running untrusted code: Testing an external contributor’s PR or a new dependency’s install script on your laptop exposes local SSH keys and cloud CLI logins sitting in the same user account. A disposable cloud VM holds none of those secrets and lets you restrict outbound network access down to None. Keep two caveats in mind: even with network set to None, requests to the Anthropic API still leave the VM, and the session can still push to its own branch.

The guide also covers starting or checking sessions from the mobile app, using Auto-fix to resolve CI failures and review comments on PRs, and scheduling recurring routines from cron schedules or GitHub events.

GitHub Permissions and Environment Setup#

GitHub access relies on two separate layers. Signing in with GitHub only verifies your identity; repository visibility for private repos comes from installing the Claude GitHub App on the user account or organization that owns the repository. When a private repo is missing from the picker, walk through this check:

flowchart TD
  A["Private repo missing<br/>from the picker"] --> D{"Claude GitHub App installed<br/>on owning account or org?"}
  D -->|"No"| E["Install App on that account or org<br/>Org installs need owner approval"]
  D -->|"Yes"| F["Check App repo selection scope<br/>and SAML SSO authorization"]

Public repositories work with GitHub sign-in alone. In the browser flow, private organization repositories appear only after the App is installed on that organization. If you already use the gh CLI locally, running /web-setup inside Claude Code can pass your gh token instead, granting access to whatever repositories that token can reach without the GitHub App—though Team and Enterprise plans require an owner to enable Quick setup first. Auto-fix, GitHub-event routines, and projects always require the GitHub App regardless of setup path.

Once GitHub is connected, the VM needs a working test environment so the session can verify its own changes. The Default image already covers most JavaScript, Python, Go, and Rust repositories. System packages belong in a setup script, which runs as root, must exit 0, and gets cached only if it finishes within 5 minutes. Project dependency steps like npm install fit better in a SessionStart hook inside .claude/settings.json, where both local and cloud sessions execute them identically. Commands for running integration suites belong in CLAUDE.md, since your personal ~/.claude directory never enters the cloud VM.

Takeaways#

The notes below are this blog’s own interpretation, not part of the original post.

  1. Watching the logging session hit the out-of-scope cache bug, leave src/cache.js alone, and document the failure in its summary is a great model for parallel agent work. Whether you are splitting backend services or data pipelines across concurrent sessions, stating explicit file boundaries in each prompt—and instructing the agent to report rather than fix out-of-scope failures—prevents painful merge conflicts later.

  2. Whether a cloud session returns a PR you can merge quickly depends heavily on the verification command in your prompt. For data engineering tasks, asking an agent to “run a validation query comparing row counts and totals against the baseline table” beats “fix the SQL query” for the exact same reason a 40-run test loop beats a single pass: the session brings back numeric proof alongside the diff.

  3. Leaving ~/.claude behind on your laptop creates healthy pressure for engineering teams. Because cloud sessions only know how to build, test, and lint your project if those instructions live in the repository (CLAUDE.md, .claude/settings.json, shared skills, and MCP configs), onboarding a cloud VM ends up documenting the repo for new human teammates at the same time.

What to Try First#

  • Open claude.ai/code, connect GitHub, and verify that the Claude GitHub App is installed on the account or organization owning your main private repositories.
  • Pick two small backlog items that touch separate files, push your current branch, and launch both in parallel via claude --cloud—including an explicit verification command in each prompt.
  • Check whether your repository’s CLAUDE.md states the exact command to run tests; if not, add a one-line instruction today.
