# 범용 반응형 ERD 웹 구축 가이드

이 문서는 특정 프로젝트의 코드, 파일명, 시트명, 컬럼 순서, 프레임워크 또는 배포 환경에 의존하지 않는 독립 실행형 구축 명세다. 새 프로젝트에는 이 파일만 복사해 사용할 수 있다.

구현자는 입력 자료의 구조를 먼저 조사하고, 실제 자료에 맞는 변환 계층을 만든 뒤 ERD 웹을 구현해야 한다. 알려지지 않은 파일 구조를 임의로 단정하지 않는다.

## 1. 사용 방법

1. 이 파일을 새 프로젝트의 최상단에 복사한다.
2. 테이블 및 컬럼 정보가 들어 있을 가능성이 있는 자료를 프로젝트 안에 둔다.
3. 구현자에게 다음과 같이 요청한다.

```text
ERD_GUIDE.md를 기준으로 현재 프로젝트의 입력 자료를 조사하고,
범용 반응형 ERD 웹을 구현해줘.
```

입력 자료가 아직 없다면 구현자는 예제 데이터와 교체 가능한 어댑터를 제공해야 한다. 실제 자료가 있다면 예제 구조를 강요하지 말고 자료를 직접 분석한다.

## 2. 목표 기능

완성되는 웹은 다음 기능을 제공해야 한다.

- 테이블과 컬럼을 카드 형태로 표시
- 테이블 및 컬럼 사용 여부를 켜고 끄기
- 미사용 항목은 삭제하지 않고 반투명하게 구분
- 개인정보 컬럼 여부 선택
- 개인정보 식별자 유형 선택: 직접식별자, 준식별자, 해당없음
- 개인정보 처리 방식 선택: 가명화또는암호화, 구간화, 해당없음
- 컬럼별 비고 입력
- PK 표시
- 확인 가능한 경우 FK 및 명시적 관계 표시
- 설정에 따라 동일하거나 대응되는 컬럼명 사이의 관계 표시
- 테이블 드래그 재배치
- 사용 테이블은 중심부, 미사용 테이블은 외곽으로 보내는 자동 배치
- 넓은 캔버스의 상하좌우 이동 여백
- 스크롤 이동과 캔버스 드래그 이동
- 트랙패드 핀치 또는 이에 준하는 확대·축소
- 전체 맞춤 보기와 확대 비율 조절
- 전체 관계선과 PK 관련 관계선 필터
- 미사용 항목의 관계선 완전 숨김 옵션
- 선택한 테이블과 연결된 관계선을 최상단에 강하게 강조
- 관계선이 상대 테이블 방향에 따라 컬럼 행의 좌우 측면에 연결
- 컬럼을 생략하고 테이블 단위 관계만 보는 그래프 뷰
- 테이블 목록의 정렬 기준 선택과 목록 선택 시 캔버스 시야 이동
- 검색, 필터 및 간단한 통계
- 편집 결과 다운로드
- 작은 화면에서도 사용할 수 있는 반응형 UI
- 선택 사항으로 공용 상태 공유 및 여러 사용자 열람

## 3. 가장 중요한 원칙

### 입력 구조를 먼저 조사한다

다음 값을 미리 가정하지 않는다.

- 입력 파일명과 확장자
- 워크북 시트명
- 헤더가 있는 행
- 테이블 정보와 컬럼 정보가 같은 시트에 있는지 여부
- 컬럼 배치 순서
- PK 또는 FK 표현 방식
- 한글명과 영문명의 존재 여부
- 병합 셀, 다중 헤더, 빈 행 사용 방식

### 원본을 보존한다

- 입력 파일을 직접 덮어쓰지 않는다.
- 생성 데이터와 다운로드 결과는 별도 파일로 만든다.
- 원본 행 순서와 사용자가 입력한 값을 가능한 한 보존한다.
- 자동 판단값과 원본에 명시된 값을 구분한다.

### 불확실성을 숨기지 않는다

- 확실한 구조는 자동 매핑한다.
- 여러 해석이 가능한 경우 후보와 근거를 제시한다.
- 핵심 매핑이 불명확할 때만 사용자에게 짧게 확인한다.
- 개인정보 여부와 관계 추론은 초기 제안값임을 명시한다.

## 4. 지원할 입력 자료

우선순위는 프로젝트에 실제로 존재하는 자료에 따라 결정한다.

- Excel: `.xlsx`, `.xls`, `.xlsm`
- 텍스트 표: `.csv`, `.tsv`
- 구조화 데이터: `.json`, `.yaml`
- 데이터베이스 정의: SQL DDL, 스키마 덤프, ORM 스키마
- 문서형 정의서: Markdown, Word, PDF
- 여러 파일로 나뉜 테이블·컬럼·인덱스·관계 정의서

문서나 PDF처럼 구조가 불명확한 자료는 먼저 표를 추출하고, 추출 결과를 검증한 뒤 사용한다.

## 5. 입력 자료 탐색 절차

### 5.1 파일 목록 작성

프로젝트 안에서 후보 파일을 찾고 다음 정보를 기록한다.

- 경로와 파일 형식
- 파일 크기와 수정 시각
- 워크북이면 전체 시트 목록
- 데이터가 존재하는 행과 열 범위
- 숨김 시트 여부

임시 파일, 잠금 파일, 이미 생성된 다운로드 결과와 백업본은 원본 후보에서 구분한다.

### 5.2 워크북 구조 조사

모든 시트를 대상으로 다음을 확인한다.

- 첫 20~50개 행의 값
- 헤더 후보 행
- 병합 셀과 반복 헤더
- 빈 행을 경계로 나뉜 여러 표
- 수식 셀과 표시값
- 숨김 행과 숨김 열
- 동일한 테이블명이 반복되는 방식

시트 이름만으로 역할을 결정하지 않는다. 이름은 단서로만 사용하고 실제 헤더와 데이터 패턴을 함께 본다.

### 5.3 시트 역할 추론

각 표 또는 시트에 대해 아래 역할의 가능성을 평가한다.

- 테이블 목록
- 컬럼 목록
- 테이블과 컬럼이 합쳐진 목록
- PK 또는 인덱스 목록
- FK 또는 관계 목록
- 코드 정의
- 설명 및 메타데이터
- 변경 이력이나 표지처럼 ERD 입력이 아닌 자료

역할 판단에는 헤더 유사어와 실제 값의 형태를 함께 사용한다.

| 표준 의미 | 가능한 표현 예시 |
|---|---|
| 테이블명 | table, table_name, entity, 엔터티, 테이블, 오브젝트명 |
| 컬럼명 | column, column_name, field, attribute, 속성, 항목명 |
| 한글명 | logical_name, display_name, 논리명, 한글명, 설명명 |
| 데이터 타입 | type, data_type, datatype, 자료형, 타입 |
| PK | pk, primary_key, primary, 기본키, 주키 |
| FK | fk, foreign_key, reference, 참조키, 외래키 |
| 설명 | description, comment, definition, 비고, 설명 |
| 순서 | ordinal, sequence, order, seq, 순번, 위치 |

유사어 비교 시 대소문자, 앞뒤 공백, 밑줄, 하이픈과 괄호를 정규화한다.

### 5.4 헤더 행 탐지

헤더가 첫 행이라는 가정을 하지 않는다. 다음 특징을 종합해 헤더 후보를 찾는다.

- 문자열 비율이 높음
- 아래 행들과 데이터 타입 분포가 다름
- 표준 의미 유사어가 여러 개 존재
- 병합된 제목 행 바로 아래에 위치
- 이후 여러 행이 유사한 구조로 반복

다중 헤더는 상위·하위 헤더를 결합해 내부 키를 만든다. 예를 들어 `컬럼 정보` 아래의 `영문명`은 `컬럼 정보 / 영문명`으로 취급할 수 있다.

### 5.5 필드 매핑 확정

최소 필수 필드는 다음 두 가지다.

- 테이블을 구분할 수 있는 값
- 컬럼을 구분할 수 있는 값

가능하면 다음 필드도 매핑한다.

- 테이블 논리명과 물리명
- 컬럼 논리명과 물리명
- 데이터 타입과 길이
- nullable 여부와 기본값
- PK 여부 및 PK 순서
- FK 대상 테이블과 컬럼
- 인덱스
- 테이블 및 컬럼 설명
- 원본 파일, 시트와 행 번호

자동 매핑 결과가 불확실하면 구현 전에 다음처럼 요약한다.

```text
테이블 식별자 후보: A열 "Entity", D열 "Object Name"
컬럼 식별자 후보: F열 "Attribute"
PK 후보: J열 "Key Type"
```

필수 필드 후보가 하나뿐이고 데이터 패턴이 일관되면 자동 진행한다. 후보가 여러 개이고 결과가 크게 달라질 때만 확인을 요청한다.

## 6. 내부 표준 데이터 모델

입력 형식과 화면을 직접 결합하지 말고, 먼저 아래와 같은 표준 모델로 변환한다. 실제 구현 언어에 맞게 타입은 조정할 수 있다.

```ts
type ErdTable = {
  id: string;
  physicalName: string;
  logicalName?: string;
  description?: string;
  included: boolean;
  source?: SourceReference;
  columns: ErdColumn[];
};

type ErdColumn = {
  id: string;
  physicalName: string;
  logicalName?: string;
  dataType?: string;
  nullable?: boolean;
  defaultValue?: string;
  primaryKey: boolean;
  primaryKeyOrder?: number;
  foreignKeys?: ForeignKeyReference[];
  included: boolean;
  personal: boolean;
  identifierType: "직접식별자" | "준식별자" | "해당없음";
  treatment: "가명화또는암호화" | "구간화" | "해당없음";
  note: string;
  source?: SourceReference;
};

type ForeignKeyReference = {
  targetTable: string;
  targetColumn: string;
  source: "explicit" | "inferred";
};

type SourceReference = {
  file: string;
  sheet?: string;
  row?: number;
  columnMap?: Record<string, number | string>;
};
```

내부 ID는 화면 상태를 안정적으로 유지할 수 있어야 한다. 행 번호만으로 ID를 만들면 입력 정렬이 바뀔 때 기존 편집 상태와 연결되지 않을 수 있으므로, 가능하면 파일 식별자와 테이블·컬럼 물리명을 조합한다.

## 7. 관계 추론 규칙

관계는 신뢰도가 높은 순서로 적용한다.

1. 입력 자료에 명시된 FK
2. DDL 또는 ORM 스키마의 참조 정의
3. 별도 관계·인덱스 정의 자료
4. 테이블명, 컬럼명과 데이터 타입을 함께 사용한 추론
5. 정규화된 컬럼명 일치

추론 관계는 명시적 관계와 시각적으로 구분할 수 있어야 한다.

기본 컬럼명 정규화 후보:

```text
앞뒤 공백 제거
대문자 또는 소문자로 통일
연속 공백 정리
선택적으로 밑줄과 하이픈 차이 흡수
```

같은 컬럼명 그룹을 모두 연결할지, PK가 포함된 조합만 연결할지는 필터로 선택할 수 있게 한다. 데이터 타입이 명백히 호환되지 않으면 자동 연결에서 제외하거나 낮은 신뢰도로 표시한다.

## 8. 개인정보 초기값 판단

개인정보 값은 원본에 명시된 분류를 최우선으로 사용한다. 명시값이 없을 때만 컬럼 물리명, 논리명과 설명 등 메타데이터를 이용해 보수적으로 추론한다.

직접식별자 후보:

- 성명, 전화번호, 이메일과 주소
- 주민·여권·면허 등 고유 식별번호
- 계정과 직접 연결되는 고유 ID

준식별자 후보:

- 생년 또는 연령, 성별과 지역
- IP 주소
- 고객번호나 기기 식별자처럼 다른 정보와 결합해 식별 가능한 값
- 직업, 등급과 이용 패턴

초기 처리 방식 예시:

- 직접식별자: 가명화또는암호화
- 연속형 준식별자: 구간화
- IP, 고객번호와 기기 식별자: 가명화또는암호화
- 개인정보가 아닌 경우: 해당없음

자동 판단은 검토 시작점일 뿐이며 법적 판단으로 표현하지 않는다. 실제 데이터 값은 분류 목적으로 읽거나 노출하지 않는 것을 기본으로 한다.

## 9. 화면 및 상호작용 요구사항

### 테이블 카드

- 헤더에 물리명, 논리명, 사용 여부와 PK 개수 표시
- 본문에 원본 순서대로 컬럼 표시
- 컬럼 행에 PK, FK, 개인정보 상태와 사용 여부 표시
- 카드 전체가 미사용이면 반투명 처리
- 선택 중인 카드는 다른 카드보다 앞에 표시
- 드래그 핸들과 컬럼 클릭 영역을 구분

### 캔버스

- 테이블을 가로 일렬이 아닌 면 형태로 분산 배치
- 초기 테이블 집합을 캔버스 중앙에 배치
- 상하좌우에 충분한 이동 여백 제공
- 빈 영역 드래그는 캔버스 이동
- 트랙패드 두 손가락 드래그(세로 휠)와 핀치는 모두 포인터 중심 확대·축소
- 가로 스와이프는 좌우 이동
- 트랙패드는 작은 델타를 연속으로, 마우스 휠은 큰 델타를 한 번에 보낸다. 이벤트당 배율 변화를 ±25% 정도로 제한해 두 입력에서 같은 감각을 만든다
- 확대·축소를 휠 이동에 배정할지는 제품 결정이다. 한쪽에 배정했으면 다른 쪽 제스처를 반드시 남겨둔다
- 브라우저 기본 확대와 충돌하지 않도록 가능한 범위에서 제스처 처리
- 확대 중심은 포인터 또는 제스처 중심을 유지
- 테이블 이동 중 관계선을 상태 갱신 직후 다시 계산

### 관계선

- 카드 중앙이 아니라 연결 컬럼 행의 측면에 연결
- 상대 카드가 오른쪽이면 오른쪽 측면에서 출발
- 상대 카드가 왼쪽이면 왼쪽 측면에서 출발
- 테이블 위치가 서로 교차하면 연결 측면도 즉시 전환
- 기본 선도 배경에서 충분히 보이는 대비와 두께 사용
- 선택한 테이블의 표시 중인 선은 마지막에 그려 가장 위에 표시
- 선택선은 색상, 두께, 외곽선 또는 광택으로 강조
- 미사용 컬럼의 선은 흐리게 표시하거나 토글에 따라 완전히 숨김
- PK 필터에 해당하지 않는 선은 흐리게 남기지 않고 완전히 숨김
- 카드가 컬럼을 페이지로 나눠 보여주면, 공유 컬럼이 양쪽 현재 페이지에 동시에 있을 확률이 낮다. 이때 관계선을 버리면 연결이 수십 개인 테이블도 선이 하나도 없어 보인다
- 한쪽 행이 다른 페이지에 있으면 선을 버리지 않고 카드 위·아래 모서리에 물려 다른 점선 패턴으로 표시한다. 어느 카드로 가는지와 어느 방향으로 페이지를 넘겨야 하는지는 남는다
- 모서리 앵커까지 모두 그리면 화면이 과밀해진다. 정확한 행 연결은 항상 그리고, 모서리 앵커는 선택한 테이블에 한정하는 것을 기본으로 한다
- 카드 머리글과 바닥글 높이를 CSS에서 고정하고 행 위치를 산술로 계산한다. 내용에 따라 높이가 변하면 선 끝점이 행에서 어긋나고, 확대할수록 눈에 띈다

### 관계 그래프 뷰

컬럼 카드는 컬럼 단위 검토에 강하지만, 스키마 전체의 연결 구조를 볼 수는 없다. 컬럼을 생략하고 테이블만 노드로 두는 힘 기반 그래프 뷰를 함께 제공한다. 두 뷰는 같은 선택 상태와 같은 관계 추론 규칙을 공유한다.

- 노드는 테이블, 엣지는 테이블 쌍이다. 공유 키가 하나라도 있으면 연결로 본다
- 엣지 굵기는 공유 키 수, 노드 크기는 연결 수로 인코딩한다
- 색은 업무 세그먼트, 테두리는 테이블 역할(마스터·이력·집계·상세)에 배정한다. 두 축을 색 하나에 겹쳐 담지 않는다
- 세그먼트와 역할은 테이블명 기반 제안이므로 업무 검토가 필요하다고 화면에 명시한다
- `공유 키 최소` 필터로 약한 연결을 걸러낸다. 기본값은 1이어야 한다. 사용자가 기준을 올리면 그 기준에서 고립되는 노드가 드러난다
- 고립 노드는 색이 아닌 형태(점선 테두리)와 이름 상시 표시로 구분한다
- 노드 좌표는 필터·정렬·검토값 변경에도 유지한다. 매번 다시 씨딩하면 배치가 흔들려 사용자가 위치로 기억한 맥락이 사라진다
- 초기 좌표는 고정 규칙(세그먼트별 원주 배치)으로 만든다. 같은 입력은 항상 같은 배치에서 시작해야 두 사람이 같은 화면을 이야기할 수 있다
- 세그먼트별 인력을 약하게 주면 색 범례가 화면의 영역으로 읽힌다
- 노드를 끌 때만 고정하고 손을 떼면 시뮬레이션에 되돌린다. 클릭으로 영구 고정되면 사용자가 해제 방법을 찾지 못한다
- 클릭 선택은 고정, 호버는 그 위에 얹는다. 호버가 선택을 덮으면 이웃 이름을 읽으려 마우스를 옮기는 순간 맥락이 사라진다
- 이웃 이름은 개수와 무관하게 모두 표시한다. 허브일수록 이름이 더 필요하다
- 범례 패널이 노드를 가리지 않도록 배치 중심과 경계를 패널 폭만큼 밀어둔다

### 편집 패널

컬럼을 선택하면 다음을 편집할 수 있어야 한다.

- 필요 컬럼 여부
- 개인정보 여부
- 개인정보 식별자 유형
- 개인정보 처리 방식
- 비고

개인정보 여부를 끄면 식별자 유형과 처리 방식을 `해당없음`으로 정리하는 것을 기본 동작으로 한다. 다시 켰을 때 이전 값을 복구할지는 제품 정책에 따라 결정한다.

## 10. 반응형 설계

- 상단 통계 영역은 가능한 작게 유지한다.
- 넓은 화면에서는 캔버스와 상세 패널을 동시에 표시한다.
- 작은 화면에서는 상세 패널을 오버레이 또는 바텀시트로 전환한다.
- 검색과 필터는 줄바꿈 또는 축약이 가능해야 한다.
- 터치 환경에서는 충분한 클릭 영역을 제공한다.
- 모바일에서도 캔버스 이동과 카드 선택이 충돌하지 않아야 한다.
- 화면 크기에 따라 초기 확대 비율과 전체 맞춤 계산을 다시 수행한다.

## 11. 상태 저장

### 로컬 저장

최소한 다음 상태를 브라우저에 저장할 수 있다.

- 테이블 및 컬럼 사용 여부
- 개인정보 분류와 비고
- 테이블 위치와 확대 비율
- 관계선 필터

입력 자료의 버전 또는 해시를 저장 키에 포함해 다른 스키마의 상태가 잘못 적용되지 않게 한다.

### 공용 상태 공유

다른 사람이 동일한 화면을 보게 하려면 서버 저장소를 사용한다. 데이터베이스 종류는 배포 환경에 맞게 선택한다.

권장 공용 상태:

- 표준화된 테이블 및 컬럼 데이터
- 테이블 위치와 확대 비율
- 표시 필터
- revision과 저장 시각

기본 공유 방식은 명시적인 `현재 상태 공유` 버튼이다. 최초 공유 전에는 기존 사용자의 로컬 상태를 덮어쓰지 않는다.

공용 상태를 조회하는 화면은 일정 주기로 새 revision을 확인할 수 있다. 사용자가 로컬에서 편집 중이면 원격 상태로 즉시 덮어쓰지 말고 충돌 가능성을 알려야 한다.

완전한 동시 편집이 필요한 경우 사용자 식별, 작업 단위 변경 기록, 낙관적 잠금 또는 CRDT, 실시간 전송, 충돌 UI와 변경 이력이 추가로 필요하다.

공개 사이트에서 쓰기 API를 익명으로 열면 링크를 아는 누구나 상태를 변경할 수 있다. 읽기 전용 공유, 편집자 인증 또는 별도 공유 키를 고려한다.

## 12. 다운로드 및 원본 순서 보존

입력이 표 형식 파일이면 가능한 한 원본 파일을 복제한 후 결과 컬럼을 추가한다. 원본의 기존 셀, 스타일, 시트와 행 순서를 유지한다.

기본 추가 컬럼:

1. 사용여부
2. 개인정보 여부
3. 개인정보 식별자 유형
4. 개인정보 처리방식
5. 비고

추가 위치는 고정 열 번호가 아니라 실제 사용 중인 마지막 열의 오른쪽으로 계산한다. 테이블과 컬럼 정보가 여러 시트에 나뉘어 있다면 컬럼 단위 정보가 존재하는 시트에 추가한다.

입력 구조가 원본 형태로 되돌리기 어려우면 원본 보존 사본과 별도 결과 시트, 표준화된 새 Excel, CSV 또는 JSON 내보내기 중 적절한 방식을 제공한다. 각 결과 행에는 원본 파일·시트·행 참조를 유지해 역매핑할 수 있게 한다.

## 13. 구현 구조 권장안

특정 프레임워크를 강제하지 않는다. 기존 프로젝트의 기술 스택과 배포 환경을 우선한다.

```text
입력 탐색기
  → 형식별 파서
  → 필드 매핑 및 검증
  → 표준 ERD 모델
  → 관계 및 개인정보 초기값 추론
  → 반응형 ERD 화면
  → 로컬/공용 상태 저장
  → 원본 기반 결과 내보내기
```

모듈 경계 예시:

- `input-discovery`: 파일, 시트와 헤더 탐색
- `input-adapters`: Excel, CSV, JSON과 DDL 파서
- `schema-mapper`: 입력 필드와 표준 모델 매핑
- `classification`: 개인정보 초기 판단
- `relationships`: 명시적 및 추론 관계 생성
- `layout`: 초기 및 자동 배치
- `canvas`: 확대, 이동, 드래그와 선 렌더링
- `state`: 로컬 및 공용 상태
- `export`: 결과 파일 생성

## 14. 성능 기준

- 관계선 계산과 그리기는 데이터 변환과 분리한다.
- 테이블 이동 중 전체 화면을 불필요하게 다시 만들지 않는다.
- 캔버스 또는 SVG 레이어는 위치 변경에 맞춰 효율적으로 갱신한다.
- 동일 컬럼명 그룹이 큰 경우 모든 조합 생성에 상한이나 경고를 둔다.
- 검색 및 필터는 메모이제이션을 고려한다.
- 수백 개 테이블에서는 카드 가상화, 관계선 공간 인덱스 또는 단계적 렌더링을 검토한다.
- 브라우저 픽셀 비율을 고려하되 캔버스 해상도 상한을 둔다.

### 최적화 순서

체감 지연은 대개 관계 추론이 아니라 프레임마다 반복되는 렌더 작업에서 나온다. 80개 테이블·5,800개 컬럼 규모에서 추론 자체는 한 자리 밀리초였고, 팬·줌이 느린 원인은 전부 렌더 쪽이었다. 다음 순서로 확인한다.

1. **프레임마다 무엇이 다시 계산되는지 센다.** 포인터 이동 한 번에 몇 개의 DOM 속성이 쓰이는지가 첫 지표다. 링크마다 선 요소를 갱신하면 링크 1,200개에서 프레임당 5,000회에 가까운 속성 쓰기가 발생한다.
2. **뷰 변환은 좌표 재계산이 아니라 변환 한 번으로 처리한다.** 관계선을 화면 좌표로 그리면 팬·줌마다 모든 경로를 다시 만든다. 카드와 같은 월드 좌표계에 그리고 같은 변환을 레이어에 적용하면 이동·확대는 속성 두 개 갱신으로 끝난다. 선 굵기는 `vector-effect: non-scaling-stroke`로 유지하고, 확대 시 선이 얇아 보이면 배율에 맞춰 굵기를 보정한다.
3. **같은 스타일의 선은 하나의 path로 합친다.** 굵기 구간별로 묶어 일반·강조 두 벌만 유지하면 프레임당 갱신이 수천 회에서 8회로 줄고 굵기 인코딩은 유지된다.
4. **힘 기반 배치는 수렴하면 멈춘다.** 계속 도는 루프는 다른 상호작용의 프레임 예산을 잡아먹는다. 감쇠 계수 하한이나 틱 상한에서 정지하고, 드래그·리사이즈·데이터 변경 때만 재가동한다.
5. **컬럼 단위 파생값은 한 번만 계산해 캐시한다.** 기본 개인정보 분류나 조인 키를 정규식으로 매번 구하면, 관계선을 그릴 때마다 컬럼 수의 몇 배에 달하는 정규식 실행이 쌓인다.
6. **렌더를 한 프레임으로 합치고 선택 변경은 부분 갱신으로 처리한다.** 선택만 바뀌었으면 클래스와 상세 패널만 갱신한다. 카드 수백 장을 다시 만들 이유가 없다.
7. **싼 조건으로 먼저 걸러낸다.** 화면 밖 카드, 현재 페이지 밖 행처럼 정수 비교로 끝나는 조건을 경로 문자열 생성과 상태 조회보다 앞에 둔다.
8. **웹폰트를 재검토한다.** 한글 웹폰트는 수백 KB에서 수 MB다. 시스템 한글 스택으로 충분한 화면이면 첫 렌더가 폰트를 기다리지 않는다.

### 흔한 함정

측정 없이 원인을 추정하면 대부분 틀린다. 다음은 실제로 오래 헤맨 항목이다.

- **절대배치 SVG의 기본 크기.** `position: absolute; inset: 0`만 준 `<svg>`는 늘어나지 않고 기본 300×150 뷰포트를 쓴다. 그 박스 밖의 선은 전부 잘려 좌상단에만 조각이 남는다. `width: 100%; height: 100%`를 명시한다.
- **포인터 캡처가 클릭을 삼킨다.** 드래그를 위해 상위 요소에서 `setPointerCapture`를 호출하면 이후 `click`이 캡처 요소로 전달되고 자식 노드의 클릭 처리기는 실행되지 않는다. 이동 거리가 임계값 이하인 `pointerup`을 클릭으로 판정한다.
- **ARIA 상태 값.** `aria-current`나 `aria-pressed`는 `"true"`/`"false"` 문자열이다. HTML 불리언 속성처럼 빈 문자열로 쓰면 `[aria-current='true']` 선택자가 걸리지 않아 강조가 사라진다.
- **SVG에는 `hidden` 프로퍼티가 없다.** `el.hidden = false`는 속성을 지우지 않으므로 호스트의 `[hidden] { display: none }` 규칙이 계속 적용된다. 속성을 직접 다룬다.
- **프레젠테이션 속성의 CSS 변수.** `fill="var(--x)"`는 적용되지 않는다. `style="fill: var(--x)"`를 쓴다.
- **한국어 콜레이션.** `localeCompare(b, 'ko')`는 한글을 라틴 문자보다 앞에 둔다. 접두어가 영문인 테이블이 전부 목록 끝으로 밀린다. 엑셀·윈도우와 같은 숫자 → 영문 → 가나다 순서가 필요하면 `'en'`을 쓴다.
- **숨은 탭의 `requestAnimationFrame`.** 백그라운드 탭에서는 콜백이 실행되지 않는다. rAF에 렌더를 위임했다면 자동화 검증에서 "동작하지 않는다"로 오판할 수 있다. 동기 경로로 상태를 확인한다.

## 15. 접근성 기준

- 모든 토글에 접근 가능한 이름과 현재 상태 제공
- 키보드로 테이블 및 컬럼 선택 가능
- 가능하면 키보드로 카드 위치 이동 가능
- 색상만으로 PK, 개인정보와 미사용 상태를 구분하지 않음
- 포커스 표시 유지
- 입력 필드에 명시적 레이블 제공
- 애니메이션 감소 설정을 존중

## 16. 검증 절차

### 입력 검증

- 모든 후보 파일과 시트를 조사했는가?
- 헤더 행을 고정값으로 가정하지 않았는가?
- 테이블 및 컬럼 매핑 근거가 있는가?
- 원본 행 참조가 보존되는가?
- 중복 테이블명과 중복 컬럼을 안전하게 처리하는가?

### 기능 검증

- 테이블과 컬럼 사용 토글이 즉시 화면에 반영되는가?
- 컬럼 사용 상태가 관계선에도 즉시 반영되는가?
- PK 필터에서 비대상 선이 완전히 사라지는가?
- 미사용 관계선 숨김이 즉시 반영되는가?
- 선택 테이블의 선이 다른 선보다 위에 보이는가?
- 테이블을 좌우로 교차 이동하면 연결 측면이 바뀌는가?
- 캔버스가 상하좌우로 이동하는가?
- 두 손가락 드래그·핀치 확대와 드래그 이동이 의도대로 분리되는가?
- 화면 크기가 달라도 주요 조작이 가능한가?
- 관계 그래프에서 노드 클릭이 테이블을 선택하고, 그 선택이 호버 중에도 유지되는가?
- 그래프의 고립 노드 수가 `공유 키 최소` 값에 따라 바뀌는가?
- 필터나 정렬을 바꿔도 그래프 노드 위치가 유지되는가?
- 확대·축소와 이동 중 프레임이 끊기지 않는가?

### 데이터 검증

- 화면의 테이블 및 컬럼 수가 원본과 일치하는가?
- PK와 FK가 원본 정의와 일치하는가?
- 원본 순서가 다운로드 결과에 유지되는가?
- 추가 분류 컬럼의 값이 화면과 일치하는가?
- 비고의 빈 값과 입력값이 구분되는가?

### 공유 검증

- 최초 공용 상태가 없을 때 로컬 데이터를 덮어쓰지 않는가?
- 공유 저장 후 다른 브라우저에서 같은 상태가 보이는가?
- 편집 중인 로컬 화면을 폴링이 덮어쓰지 않는가?
- 권한 없는 사용자의 쓰기 범위가 의도와 일치하는가?

## 17. 배포 안전 수칙

- 새 프로젝트는 새 배포 프로젝트와 새 저장소를 사용한다.
- 다른 프로젝트에서 복사한 배포 ID, 사이트 ID, 데이터베이스 ID 또는 비밀값을 재사용하지 않는다.
- 가이드에는 실제 배포 ID나 인증 정보를 기록하지 않는다.
- 로컬 실행과 파일 복사만으로 기존 사이트가 변경되어서는 안 된다.
- 배포 전 대상 사이트 이름과 공개 범위를 확인한다.
- 기존 사이트를 갱신할 때는 정확한 대상임을 확인한 뒤 배포한다.
- 공용 상태 데이터베이스 역시 환경별로 분리한다.

## 18. 완료 조건

- 입력 구조를 자동 조사하고 사용한 매핑을 설명할 수 있다.
- 고정된 파일명, 시트명 또는 열 번호 없이 대상 자료를 처리한다.
- 표준 모델과 입력 어댑터가 분리되어 있다.
- 요구된 분류 및 비고를 편집할 수 있다.
- 관계선, 필터, 자동 배치, 드래그, 이동과 확대·축소가 동작한다.
- 미사용 항목은 삭제되지 않고 시각적으로 구분된다.
- 편집 결과를 원본과 연결 가능한 형태로 다운로드할 수 있다.
- 반응형 화면과 접근성 기본 검증을 통과한다.
- 새 프로젝트의 배포가 다른 프로젝트나 기존 공개 링크에 영향을 주지 않는다.
