# 스키마 분석용 ERD 웹 에이전트 작업 명세

이 문서는 AI 코딩 에이전트가 읽고 그대로 수행하는 작업 명세다. 프로젝트 안의 스키마 자료를 조사해 테이블·컬럼 검토용 반응형 ERD 웹을 만든다. 특정 파일명, 시트명, 열 순서, 프레임워크, 배포 환경을 전제하지 않으므로 어느 프로젝트에나 이 파일 하나만 복사해 쓴다.

에이전트는 아래 순서를 지킨다.

1. 작업 규칙(1장)을 끝까지 읽는다. 모든 단계에 적용된다.
2. 2장의 단계를 번호순으로 수행하고, 게이트마다 정해진 출력을 남긴다.
3. 3장의 검증을 모두 돌린 뒤 4장 형식으로 최종 보고한다.
4. 구현 중 막히면 부록(성능 최적화 순서, 흔한 함정)을 먼저 확인한다.

## 0. 사용법 (사람용)

1. 이 파일을 프로젝트 최상단에 둔다.
2. 스키마 자료(정의서, DDL, 스키마 덤프 등)를 프로젝트 안에 넣는다.
3. 에이전트에게 아래처럼 요청한다.

```text
ERD_AGENT_SPEC.md를 읽고 그대로 수행해줘.
스키마 자료부터 조사해서 매핑 보고서를 먼저 보여주고,
판단이 갈리는 매핑이 없으면 확인 없이 구현과 검증까지 끝내줘.
```

자료 위치를 알고 있다면 `입력 자료는 ./schema/ 경로에 있음` 과 같이 경로 안내를 한 줄 덧붙인다. 자료가 아직 없으면 에이전트는 예제 데이터와 교체 가능한 입력 어댑터로 시작한다.

## 1. 작업 규칙

### 1.1 반드시 지킬 것

- **R1. 입력 구조는 조사해서 확정한다.** 파일명·확장자, 시트명, 헤더 행 위치, 열 순서, 테이블·컬럼 정보가 같은 시트에 있는지, PK·FK 표기 방식, 한글명·영문명 유무, 병합 셀·다중 헤더·빈 행 사용 방식을 가정하지 않는다.
- **R2. 원본은 읽기 전용이다.** 생성 데이터와 내보내기 결과는 별도 파일로 만든다. 원본 행 순서와 사용자가 입력한 값을 보존한다.
- **R3. 명시값과 추론값을 구분한다.** 원본에 적힌 값과 에이전트가 추론한 값(관계, 개인정보 분류, 세그먼트, 테이블 역할)을 데이터 모델과 화면 양쪽에서 구분한다. 추론값은 화면에 "제안값"으로 표시한다.
- **R4. 데이터 값은 읽지 않는다.** 분류는 메타데이터(컬럼 물리명, 논리명, 설명, 타입)로만 한다. 실제 데이터 행의 값을 분류 목적으로 읽거나 화면에 노출하지 않는다.
- **R5. 기존 스택을 따른다.** 프로젝트에 기술 스택과 배포 방식이 있으면 그대로 쓴다. 없으면 의존성이 가장 적은 구성을 고르고 선택 이유를 보고한다.
- **R6. 모듈을 분리한다.** 입력 어댑터, 표준 모델, 추론, 화면, 상태 저장, 내보내기가 서로의 내부 구현에 기대지 않게 만든다. 컬럼 카드 뷰와 관계 그래프 뷰는 같은 선택 상태와 같은 추론 결과를 공유한다. 모듈 경계는 아래를 기본으로 한다.

  ```text
  input-discovery  파일·시트·헤더 탐색
  input-adapters   Excel, CSV, JSON, DDL 파서
  schema-mapper    입력 필드 → 표준 모델 매핑
  classification   개인정보 초기 판단
  relationships    명시·추론 관계 생성
  layout           초기·자동 배치
  canvas           확대, 이동, 드래그, 선 렌더링
  state            로컬·공용 상태
  export           결과 파일 생성
  ```
- **R7. 성능은 측정으로 판단한다.** 추정으로 원인을 정하지 않는다. 팬·줌·드래그 중 프레임당 DOM 속성 쓰기 수와 경로 재생성 수를 세어 보고한다.

### 1.2 사용자에게 묻는 경우

아래 세 경우에만 짧게 묻는다. 그 밖에는 근거를 보고하고 진행한다.

- **Q1.** 테이블 또는 컬럼 식별자 후보가 둘 이상이고, 어느 쪽을 고르느냐에 따라 테이블 수나 컬럼 수가 달라질 때
- **Q2.** 같은 정의서의 여러 버전(날짜별 사본 등)이 있어 기준 원본을 정할 수 없을 때
- **Q3.** 배포 대상 사이트나 공개 범위를 정해야 할 때

### 1.3 하지 말 것

- 원본 파일 덮어쓰기
- 다른 프로젝트에서 복사한 배포 ID, 사이트 ID, 데이터베이스 ID, 비밀값 재사용
- 명세, 코드, 설정 파일에 실제 배포 ID나 인증 정보 기록
- 로컬 실행이나 파일 복사만으로 기존 사이트가 바뀌는 구성
- 개인정보 자동 분류 결과를 법적 판단처럼 표현하기
- 미사용으로 표시한 테이블·컬럼을 모델이나 내보내기 결과에서 삭제하기

## 2. 작업 단계

### 단계 1. 입력 조사

**대상 형식.** 실제로 존재하는 자료를 우선한다.

- Excel: `.xlsx`, `.xls`, `.xlsm`
- 텍스트 표: `.csv`, `.tsv`
- 구조화 데이터: `.json`, `.yaml`
- 데이터베이스 정의: SQL DDL, 스키마 덤프, ORM 스키마
- 문서형 정의서: Markdown, Word, PDF (표를 먼저 추출하고 추출 결과를 검증한 뒤 쓴다)
- 테이블·컬럼·인덱스·관계가 여러 파일로 나뉜 정의서

**1-1. 후보 파일 목록.** 경로, 형식, 크기, 수정 시각을 기록한다. 워크북이면 전체 시트 목록, 숨김 시트 여부, 데이터가 있는 행·열 범위도 기록한다. 임시 파일, 잠금 파일, 이전 내보내기 결과, 백업본은 원본 후보에서 분리한다.

**1-2. 시트 구조.** 모든 시트에서 앞 20-50행을 읽고 다음을 확인한다.

- 헤더 후보 행
- 병합 셀과 반복 헤더
- 빈 행을 경계로 나뉜 여러 표
- 수식 셀과 표시값
- 숨김 행과 숨김 열
- 같은 테이블명이 반복되는 방식

**1-3. 시트 역할 분류.** 각 표를 테이블 목록, 컬럼 목록, 테이블·컬럼 통합 목록, PK·인덱스 목록, FK·관계 목록, 코드 정의, 설명·메타데이터, ERD 입력 아님(변경 이력, 표지 등) 중 하나로 분류한다. 시트 이름은 단서로만 쓰고 헤더 유사어와 값의 형태로 판정한다.

| 표준 의미 | 헤더 유사어 |
|---|---|
| 테이블명 | table, table_name, entity, 엔터티, 테이블, 오브젝트명 |
| 컬럼명 | column, column_name, field, attribute, 속성, 항목명 |
| 한글명 | logical_name, display_name, 논리명, 한글명, 설명명 |
| 데이터 타입 | type, data_type, datatype, 자료형, 타입 |
| PK | pk, primary_key, primary, 기본키, 주키 |
| FK | fk, foreign_key, reference, 참조키, 외래키 |
| 설명 | description, comment, definition, 비고, 설명 |
| 순서 | ordinal, sequence, order, seq, 순번, 위치 |

비교 전에 대소문자, 앞뒤 공백, 밑줄, 하이픈, 괄호를 정규화한다.

**1-4. 헤더 행 탐지.** 첫 행이 헤더라고 가정하지 않는다. 아래 신호를 종합한다.

- 문자열 비율이 높다
- 아래 행과 데이터 타입 분포가 다르다
- 표준 의미 유사어가 여러 개 있다
- 병합된 제목 행 바로 아래에 있다
- 이후 여러 행이 같은 구조로 반복된다

다중 헤더는 상위·하위 헤더를 이어 내부 키로 쓴다. 예: `컬럼 정보` 아래의 `영문명` → `컬럼 정보 / 영문명`.

**1-5. 필드 매핑.** 필수 필드는 테이블 식별값과 컬럼 식별값 두 가지다. 가능하면 테이블·컬럼 논리명과 물리명, 데이터 타입과 길이, nullable, 기본값, PK 여부와 순서, FK 대상 테이블·컬럼, 인덱스, 테이블·컬럼 설명, 원본 파일·시트·행 번호까지 매핑한다.

**게이트 1: 매핑 보고서.** 구현 전에 아래 형식으로 보고한다. Q1·Q2에 해당하지 않으면 보고 후 바로 단계 2로 간다.

```text
[입력 파일] schema/table_spec.xlsx (시트 4개, 숨김 1개)
[시트 역할] 테이블목록=Tables(헤더 3행) / 컬럼목록=Columns(헤더 2-3행 병합) / 제외=History
[필드 매핑] 테이블=A열 "Entity" / 컬럼=F열 "Attribute" / PK=J열 "Key Type"
[대안 후보] 테이블=D열 "Object Name" (A열과 값이 다른 행 없음)
[원본 집계] 테이블 42개, 컬럼 1,318개, 명시 PK 40개, 명시 FK 0개
[제외 파일] ~$table_spec.xlsx(잠금 파일), export_result.xlsx(이전 결과)
[미확정] 없음
```

위 값은 형식을 보여주는 예시다. 실제 조사 결과로 채운다.

### 단계 2. 표준 모델 변환

입력 형식과 화면을 직접 연결하지 않는다. 먼저 아래 표준 모델로 변환하고 화면은 이 모델만 읽는다. 타입은 구현 언어에 맞게 조정한다.

```ts
type ValueOrigin = "explicit" | "suggested";

type ErdTable = {
  id: string;
  physicalName: string;
  logicalName?: string;
  description?: string;
  included: boolean;
  source?: SourceReference;
  columns: ErdColumn[];
};

type ErdColumn = {
  id: string;
  physicalName: string;
  logicalName?: string;
  dataType?: string;
  nullable?: boolean;
  defaultValue?: string;
  primaryKey: boolean;
  primaryKeyOrder?: number;
  foreignKeys?: ForeignKeyReference[];
  included: boolean;
  personal: boolean;
  identifierType: "직접식별자" | "준식별자" | "해당없음";
  treatment: "가명화또는암호화" | "구간화" | "해당없음";
  classificationOrigin: ValueOrigin;
  note: string;
  source?: SourceReference;
};

type ForeignKeyReference = {
  targetTable: string;
  targetColumn: string;
  origin: "explicit" | "inferred";
  confidence?: "high" | "low";
};

type SourceReference = {
  file: string;
  sheet?: string;
  row?: number;
  columnMap?: Record<string, number | string>;
};
```

- ID는 파일 식별자와 테이블·컬럼 물리명을 조합해 만든다. 행 번호만으로 만들면 입력 정렬이 바뀔 때 기존 편집 상태와 연결이 끊긴다.
- 중복 테이블명과 중복 컬럼은 합치지 않는다. `source` 로 구분하고 경고를 남긴다.

**게이트 2: 모델 집계.** 표준 모델의 테이블 수, 컬럼 수, PK 수가 게이트 1의 원본 집계와 일치하는지 확인한다. 다르면 원인을 찾기 전에는 단계 3으로 가지 않는다.

### 단계 3. 관계·개인정보 추론

**관계 우선순위.** 신뢰도가 높은 순서로 적용한다.

1. 입력 자료에 명시된 FK
2. DDL 또는 ORM 스키마의 참조 정의
3. 별도 관계·인덱스 정의 자료
4. 테이블명, 컬럼명, 데이터 타입을 함께 쓴 추론
5. 정규화된 컬럼명 일치

컬럼명 정규화는 앞뒤 공백 제거, 대소문자 통일, 연속 공백 정리를 기본으로 하고, 밑줄과 하이픈 차이 흡수는 선택 사항으로 둔다.

- 추론 관계(4, 5)는 명시 관계와 선 모양으로 구분한다.
- 같은 이름 그룹을 모두 연결할지, PK가 포함된 조합만 연결할지는 필터로 고르게 한다.
- 데이터 타입이 명백히 호환되지 않으면 자동 연결에서 빼거나 `confidence: "low"` 로 표시한다.
- 같은 이름 그룹이 크면 모든 조합을 만들지 않는다. 그룹 크기에 상한을 두고 넘으면 경고한다.

**개인정보 초기값.** 원본에 분류가 명시돼 있으면 그 값을 쓰고 `classificationOrigin: "explicit"` 으로 둔다. 명시값이 없을 때만 메타데이터로 보수적으로 추론하고 `"suggested"` 로 둔다.

- 직접식별자 후보: 성명, 전화번호, 이메일, 주소, 주민·여권·면허 등 고유 식별번호, 계정과 직접 연결되는 고유 ID
- 준식별자 후보: 생년 또는 연령, 성별, 지역, IP 주소, 고객번호나 기기 식별자처럼 다른 정보와 결합해 식별 가능한 값, 직업, 등급, 이용 패턴

처리 방식 기본값은 이렇다.

| 대상 | 기본 처리 방식 |
|---|---|
| 직접식별자 | 가명화또는암호화 |
| 연속형 준식별자 | 구간화 |
| IP, 고객번호, 기기 식별자 | 가명화또는암호화 |
| 개인정보 아님 | 해당없음 |

**게이트 3: 추론 요약.** 명시 FK 수, 추론 관계 수(신뢰도별), 개인정보 제안 컬럼 수(직접식별자·준식별자별)를 출력한다.

### 단계 4. 화면

**4-1. 레이아웃과 반응형**

- 상단 통계 영역은 작게 유지한다.
- 넓은 화면에서는 캔버스와 상세 패널을 함께 보여준다. 좁은 화면에서는 상세 패널을 오버레이나 바텀시트로 바꾼다.
- 검색과 필터는 줄바꿈되거나 축약된다.
- 터치 환경에서는 클릭 영역을 충분히 키우고, 캔버스 이동과 카드 선택이 충돌하지 않게 한다.
- 화면 크기가 바뀌면 초기 확대 비율과 전체 맞춤을 다시 계산한다.

**4-2. 테이블 카드**

- 헤더: 물리명, 논리명, 사용 여부 토글, PK 개수
- 본문: 원본 순서대로 컬럼을 나열하고 각 행에 PK, FK, 개인정보 상태, 사용 여부를 표시
- 미사용 테이블은 카드 전체를, 미사용 컬럼은 해당 행을 반투명하게 처리한다. 삭제하지 않는다.
- 선택 중인 카드는 다른 카드보다 앞에 둔다.
- 드래그 핸들과 컬럼 클릭 영역을 분리한다.
- 카드 머리글과 바닥글 높이는 CSS로 고정하고 행 위치는 산술로 계산한다. 내용에 따라 높이가 변하면 선 끝점이 행에서 어긋나고, 확대할수록 눈에 띈다.

**4-3. 편집 패널.** 컬럼을 선택하면 필요 컬럼 여부, 개인정보 여부, 식별자 유형, 처리 방식, 비고를 편집한다. 개인정보 여부를 끄면 식별자 유형과 처리 방식을 `해당없음` 으로 정리한다. 다시 켰을 때 이전 값을 복구할지는 제품 정책으로 정하고 결정 내용을 보고한다.

**4-4. 캔버스**

- 테이블을 가로 일렬이 아니라 면 형태로 분산 배치하고, 초기 집합을 캔버스 중앙에 둔다.
- 카드를 드래그해 재배치할 수 있다. 자동 배치 버튼은 사용 테이블을 중심부로, 미사용 테이블을 외곽으로 보낸다.
- 상하좌우에 충분한 이동 여백을 둔다.
- 빈 영역 드래그와 스크롤은 캔버스 이동이다.
- 트랙패드 두 손가락 드래그(세로 휠)와 핀치는 포인터 중심 확대·축소, 가로 스와이프는 좌우 이동이다.
- 트랙패드는 작은 델타를 연속으로, 마우스 휠은 큰 델타를 한 번에 보낸다. 이벤트당 배율 변화를 ±25% 정도로 제한해 두 입력의 감각을 맞춘다.
- 확대·축소를 휠 이동에 배정할지는 제품 결정이다. 한쪽에 배정했으면 다른 쪽 제스처를 반드시 남긴다.
- 브라우저 기본 확대와 충돌하지 않게 제스처를 처리하고, 확대 중심은 포인터나 제스처 중심에 고정한다.
- 전체 맞춤 보기와 확대 비율 조절 컨트롤을 둔다.
- 테이블을 드래그하는 동안 관계선은 상태 갱신 직후 다시 계산한다.

**4-5. 관계선**

- 카드 중앙이 아니라 연결 컬럼 행의 측면에 연결한다. 상대 카드가 오른쪽이면 오른쪽, 왼쪽이면 왼쪽 측면에서 출발하고, 두 카드 위치가 교차하면 측면도 즉시 바꾼다.
- 기본 선도 배경에서 충분히 보이는 대비와 두께를 쓴다.
- 선택한 테이블의 선은 마지막에 그려 맨 위에 두고 색상, 두께, 외곽선, 광택 중 하나 이상으로 강조한다.
- 미사용 컬럼의 선은 흐리게 그리거나, 토글에 따라 완전히 숨긴다.
- PK 필터에 해당하지 않는 선은 흐리게 남기지 않고 완전히 숨긴다.
- 카드가 컬럼을 페이지로 나눠 보여주면 공유 컬럼이 양쪽 현재 페이지에 동시에 있을 확률이 낮다. 이때 선을 버리면 연결이 수십 개인 테이블도 선이 없어 보인다. 한쪽 행이 다른 페이지에 있으면 카드 위·아래 모서리에 선을 물리고 다른 점선 패턴으로 그린다. 어느 카드로 가는지, 어느 방향으로 페이지를 넘길지가 남는다.
- 정확한 행 연결은 항상 그린다. 모서리 앵커는 화면이 과밀해지지 않도록 선택한 테이블에만 그리는 것을 기본값으로 한다.

**4-6. 관계 그래프 뷰.** 컬럼 카드는 컬럼 단위 검토에 강하지만 스키마 전체의 연결 구조는 보여주지 못한다. 컬럼을 생략하고 테이블만 노드로 두는 힘 기반 그래프 뷰를 함께 만든다.

- 노드는 테이블, 엣지는 공유 키가 하나 이상인 테이블 쌍이다.
- 엣지 굵기는 공유 키 수, 노드 크기는 연결 수로 인코딩한다.
- 색은 업무 세그먼트, 테두리는 테이블 역할(마스터·이력·집계·상세)에 배정한다. 두 축을 색 하나에 겹쳐 담지 않는다.
- 세그먼트와 역할은 테이블명 기반 제안값이므로 업무 검토가 필요하다고 화면에 적는다.
- `공유 키 최소` 필터로 약한 연결을 거른다. 기본값은 1이다. 기준을 올리면 그 기준에서 고립되는 노드가 드러난다.
- 고립 노드는 색이 아닌 형태(점선 테두리)와 이름 상시 표시로 구분한다.
- 초기 좌표는 고정 규칙(세그먼트별 원주 배치)으로 만든다. 같은 입력이 항상 같은 배치에서 시작해야 두 사람이 같은 화면을 두고 이야기할 수 있다.
- 노드 좌표는 필터·정렬·검토값을 바꿔도 유지한다. 매번 다시 씨딩하면 사용자가 위치로 기억한 맥락이 사라진다.
- 세그먼트별 인력을 약하게 주면 색 범례가 화면의 영역으로 읽힌다.
- 노드는 드래그하는 동안만 고정하고 손을 떼면 시뮬레이션에 돌려준다. 클릭으로 영구 고정하면 사용자가 해제 방법을 찾지 못한다.
- 클릭 선택은 유지되고 호버는 그 위에 얹는다. 호버가 선택을 덮으면 이웃 이름을 읽으려 마우스를 옮기는 순간 맥락이 사라진다.
- 이웃 이름은 개수와 관계없이 모두 표시한다. 허브일수록 이름이 더 필요하다.
- 범례 패널이 노드를 가리지 않도록 배치 중심과 경계를 패널 폭만큼 밀어둔다.

**4-7. 목록, 검색, 통계**

- 테이블 목록에 정렬 기준 선택을 두고, 목록에서 테이블을 고르면 캔버스 시야를 그 테이블로 옮긴다.
- 검색, 필터, 간단한 통계(테이블·컬럼 수, 사용 비율, 개인정보 컬럼 수 등)를 제공한다.
- 정렬은 엑셀·윈도우와 같은 숫자 → 영문 → 가나다 순서를 기본으로 한다(부록 B의 콜레이션 항목 참고).

**4-8. 접근성**

- 모든 토글에 접근 가능한 이름과 현재 상태를 제공한다.
- 키보드로 테이블과 컬럼을 선택할 수 있게 하고, 가능하면 카드 위치도 키보드로 옮긴다.
- PK, 개인정보, 미사용 상태를 색상만으로 구분하지 않는다.
- 포커스 표시를 유지하고 입력 필드에 명시적 레이블을 둔다.
- 애니메이션 감소 설정(`prefers-reduced-motion`)을 따른다.

### 단계 5. 상태 저장과 공유

**로컬 저장.** 테이블·컬럼 사용 여부, 개인정보 분류와 비고, 테이블 위치와 확대 비율, 관계선 필터를 브라우저에 저장한다. 저장 키에 입력 자료의 버전이나 해시를 넣어 다른 스키마의 상태가 섞이지 않게 한다.

**공용 공유(선택).** 다른 사람이 같은 화면을 봐야 할 때만 서버 저장소를 쓴다. 저장소 종류는 배포 환경에 맞춘다.

- 공유 대상: 표준화된 테이블·컬럼 데이터, 테이블 위치와 확대 비율, 표시 필터, revision과 저장 시각
- 공유는 명시적인 `현재 상태 공유` 버튼으로만 한다. 최초 공유 전에는 기존 사용자의 로컬 상태를 덮어쓰지 않는다.
- 조회 화면은 주기적으로 새 revision을 확인한다. 사용자가 로컬에서 편집 중이면 원격 상태로 덮어쓰지 말고 충돌 가능성을 알린다.
- 쓰기 API를 익명으로 열면 링크를 아는 누구나 상태를 바꾼다. 읽기 전용 공유, 편집자 인증, 별도 공유 키 중 하나를 적용한다.
- 공용 상태 데이터베이스는 환경별로 분리한다.
- 완전한 동시 편집은 범위 밖이다. 필요하면 사용자 식별, 작업 단위 변경 기록, 낙관적 잠금이나 CRDT, 실시간 전송, 충돌 UI, 변경 이력이 추가로 필요하다고 보고한다.

### 단계 6. 내보내기

- 입력이 표 형식 파일이면 원본을 복제한 뒤 결과 컬럼을 추가한다. 기존 셀, 스타일, 시트, 행 순서를 유지한다.
- 추가 컬럼은 순서대로 사용여부, 개인정보 여부, 개인정보 식별자 유형, 개인정보 처리방식, 비고다.
- 추가 위치는 고정 열 번호가 아니라 실제 사용 중인 마지막 열의 오른쪽으로 계산한다.
- 테이블과 컬럼 정보가 여러 시트에 나뉘어 있으면 컬럼 단위 정보가 있는 시트에 추가한다.
- 원본 형태로 되돌리기 어려우면 원본 보존 사본과 별도 결과 시트, 표준화된 새 Excel, CSV, JSON 중 알맞은 방식을 고른다. 어느 방식이든 결과 행마다 원본 파일·시트·행 참조를 남겨 역매핑할 수 있게 한다.
- 비고가 비어 있는 경우와 입력된 경우를 구분해 내보낸다.

### 단계 7. 성능

- 관계선 계산과 그리기를 데이터 변환과 분리한다.
- 테이블을 드래그하는 동안 화면 전체를 다시 만들지 않는다. 캔버스나 SVG 레이어는 바뀐 위치만 갱신한다.
- 검색과 필터 결과는 메모이제이션한다.
- 수백 개 테이블 규모에서는 카드 가상화, 관계선 공간 인덱스, 단계적 렌더링을 검토한다.
- 브라우저 픽셀 비율을 반영하되 캔버스 해상도에 상한을 둔다.
- 느리면 부록 A 순서대로 원인을 찾는다.

## 3. 검증

아래 항목을 모두 확인하고 결과를 최종 보고에 넣는다.

**입력**

- 모든 후보 파일과 시트를 조사했다.
- 헤더 행을 고정값으로 가정하지 않았다.
- 테이블·컬럼 매핑마다 근거가 있다.
- 원본 행 참조가 모델과 내보내기 결과에 남아 있다.
- 중복 테이블명과 중복 컬럼이 합쳐지지 않고 경고로 남는다.
- 입력 어댑터를 바꿔도 화면 코드는 바뀌지 않는다.

**데이터**

- 화면의 테이블·컬럼 수가 원본 집계와 같다.
- PK와 FK가 원본 정의와 같다.
- 내보내기 결과의 행 순서가 원본과 같고, 추가 컬럼 값이 화면과 같다.
- 비고의 빈 값과 입력값이 구분된다.

**기능**

- 테이블·컬럼 사용 토글이 카드와 관계선에 즉시 반영된다.
- PK 필터를 켜면 비대상 선이 완전히 사라진다.
- 미사용 관계선 숨김이 즉시 반영된다.
- 선택한 테이블의 선이 다른 선보다 위에 그려진다.
- 테이블을 좌우로 교차해 옮기면 연결 측면이 바뀐다.
- 캔버스가 상하좌우로 이동한다.
- 두 손가락 드래그·핀치 확대와 드래그 이동이 의도대로 분리된다.
- 그래프 뷰에서 노드를 클릭하면 테이블이 선택되고, 호버 중에도 선택이 유지된다.
- `공유 키 최소` 값에 따라 고립 노드 수가 바뀐다.
- 필터나 정렬을 바꿔도 그래프 노드 위치가 유지된다.
- 확대·축소와 이동 중 프레임이 끊기지 않는다(프레임당 DOM 쓰기 수로 확인).

**반응형·접근성**

- 좁은 화면에서도 선택, 편집, 이동, 확대가 가능하다.
- 키보드만으로 테이블과 컬럼을 선택할 수 있다.
- 색을 빼도 PK, 개인정보, 미사용 상태를 구분할 수 있다.

**공유(구현한 경우)**

- 공용 상태가 없을 때 로컬 데이터를 덮어쓰지 않는다.
- 공유 저장 후 다른 브라우저에서 같은 상태가 보인다.
- 편집 중인 로컬 화면을 폴링이 덮어쓰지 않는다.
- 권한 없는 사용자의 쓰기 범위가 의도와 같다.

**배포 안전**

- 새 프로젝트는 새 배포 프로젝트와 새 저장소를 쓴다.
- 다른 프로젝트의 배포 ID, 사이트 ID, 데이터베이스 ID, 비밀값을 재사용하지 않았다.
- 배포 전에 대상 사이트 이름과 공개 범위를 확인했다. 기존 사이트를 갱신할 때는 정확한 대상인지 확인했다.

## 4. 최종 보고 형식

작업이 끝나면 아래 형식으로 보고한다. 실패한 검증 항목은 숨기지 말고 원인과 함께 적는다.

```text
[실행 방법] 로컬 실행 명령과 접속 주소
[기술 선택] 사용한 스택과 이유 (기존 스택을 따랐는지 여부)
[사용한 매핑] 게이트 1 보고서의 최종본
[원본 대비 집계] 테이블 / 컬럼 / PK / FK 수와 일치 여부
[추론 결과] 추론 관계 수(신뢰도별), 개인정보 제안 컬럼 수
[검증 결과] 3장 항목별 통과·실패와 실패 원인
[성능 측정] 팬·줌·드래그 중 프레임당 DOM 쓰기 수 (최적화 전후)
[사람 검토 필요] 제안값, 미확정 매핑, 정책 결정이 필요한 항목
```

## 부록 A. 성능 최적화 순서

체감 지연은 대개 관계 추론이 아니라 프레임마다 반복되는 렌더 작업에서 나온다. 80개 테이블·5,800개 컬럼 규모에서 추론 자체는 수 밀리초(ms) 단위로 완료되었고, 팬·줌 성능 저하의 주원인은 브라우저 렌더링 병목이었다. 아래 순서로 확인한다.

1. **프레임마다 무엇이 다시 계산되는지 센다.** 포인터 이동 한 번에 DOM 속성이 몇 번 쓰이는지가 첫 지표다. 링크마다 선 요소를 갱신하면 링크 1,200개에서 프레임당 5,000회에 가까운 속성 쓰기가 생긴다.
2. **뷰 변환은 좌표 재계산이 아니라 변환 한 번으로 처리한다.** 관계선을 화면 좌표로 그리면 팬·줌마다 모든 경로를 다시 만든다. 카드와 같은 월드 좌표계에 그리고 같은 변환을 레이어에 적용하면 이동·확대가 속성 두 개 갱신으로 끝난다. 선 굵기는 `vector-effect: non-scaling-stroke` 로 유지하고, 확대 시 선이 얇아 보이면 배율에 맞춰 굵기를 보정한다.
3. **같은 스타일의 선은 하나의 path로 합친다.** 굵기 구간별로 묶어 일반·강조 두 벌만 유지하면 프레임당 갱신이 수천 회에서 8회로 줄고 굵기 인코딩은 유지된다.
4. **힘 기반 배치는 수렴하면 멈춘다.** 계속 도는 루프는 다른 상호작용의 프레임 예산을 잡아먹는다. 감쇠 계수 하한이나 틱 상한에서 정지하고 드래그·리사이즈·데이터 변경 때만 재가동한다.
5. **컬럼 단위 파생값은 한 번만 계산해 캐시한다.** 기본 개인정보 분류나 조인 키를 정규식으로 매번 구하면 관계선을 그릴 때마다 컬럼 수의 몇 배에 달하는 정규식 실행이 쌓인다.
6. **렌더를 한 프레임으로 합치고 선택 변경은 부분 갱신으로 처리한다.** 선택만 바뀌었으면 클래스와 상세 패널만 갱신한다. 카드 수백 장을 다시 만들 이유가 없다.
7. **싼 조건으로 먼저 거른다.** 화면 밖 카드, 현재 페이지 밖 행처럼 정수 비교로 끝나는 조건을 경로 문자열 생성과 상태 조회보다 앞에 둔다.
8. **웹폰트를 재검토한다.** 한글 웹폰트는 수백 KB에서 수 MB다. 시스템 한글 폰트 스택으로 충분하면 첫 렌더가 폰트를 기다리지 않는다.

## 부록 B. 흔한 함정

체감 성능에 의존한 최적화는 실패하기 쉽다. 아래는 실제 구현 과정에서 확인된 기술적 시행착오와 브라우저 제약 사항이다.

- **절대배치 SVG의 기본 크기.** `position: absolute; inset: 0` 만 준 `<svg>` 는 늘어나지 않고 기본 300×150 뷰포트를 쓴다. 그 박스 밖의 선은 전부 잘려 좌상단에만 조각이 남는다. `width: 100%; height: 100%` 를 명시한다.
- **포인터 캡처가 클릭을 삼킨다.** 드래그를 위해 상위 요소에서 `setPointerCapture` 를 호출하면 이후 `click` 이 캡처 요소로 전달되고 자식 노드의 클릭 처리기는 실행되지 않는다. 이동 거리가 임계값 이하인 `pointerup` 을 클릭으로 판정한다.
- **ARIA 상태 값.** `aria-current` 나 `aria-pressed` 는 `"true"`/`"false"` 문자열이다. HTML 불리언 속성처럼 빈 문자열로 쓰면 `[aria-current='true']` 선택자가 걸리지 않아 강조가 사라진다.
- **SVG에는 `hidden` 프로퍼티가 없다.** `el.hidden = false` 는 속성을 지우지 않으므로 호스트의 `[hidden] { display: none }` 규칙이 계속 적용된다. 속성을 직접 다룬다.
- **프레젠테이션 속성의 CSS 변수.** `fill="var(--x)"` 는 적용되지 않는다. `style="fill: var(--x)"` 를 쓴다.
- **한국어 콜레이션.** `localeCompare(b, 'ko')` 는 한글을 라틴 문자보다 앞에 둔다. 접두어가 영문인 테이블이 전부 목록 끝으로 밀린다. 숫자 → 영문 → 가나다 순서가 필요하면 `'en'` 을 쓴다.
- **숨은 탭의 `requestAnimationFrame`.** 백그라운드 탭에서는 콜백이 실행되지 않는다. rAF에 렌더를 맡겼다면 자동화 검증에서 "동작하지 않는다"로 오판할 수 있다. 동기 경로로 상태를 확인한다.
