한눈에 보기#

코디네이터 에이전트를 둘지 말지를 두고 의견이 갈리지만, 핵심은 계층을 늘리거나 줄이는 문제에 있지 않습니다. 관제는 두껍게, 추론 중계는 얇게, 검증은 명시적으로 나누어 설계하면 양쪽이 말하는 장점을 함께 챙길 수 있어요.

  1. 병목의 정체: 에이전트는 동시에 여러 일을 처리하지만 사람은 한 번에 하나씩 검토합니다. 에이전트 수가 늘어날수록 병목은 코드 작성에서 사람의 판단으로 넘어갑니다.
  2. 논쟁의 정체: 찬성 쪽은 관제 부담을, 비판 쪽은 결과물 품질을 이야기합니다. ‘코디네이터’라는 한 단어 안에 성격이 다른 역할이 섞여 있어서 말이 엇갈립니다.
  3. 실천 기준: 내 선택에 따라 결과가 달라지는 결정만 사람에게 올립니다. 에이전트가 끝냈다고 알린 상태(Done)와 품질 검증을 통과한 승인 상태(Accepted)는 따로 관리합니다.
숫자의미
3계층영상이 제안한 구조: 매니저, 코디네이터, 코딩 에이전트
4+1등급코디네이터 보드의 모델 배정 단위: 작업용 A-D, 코디네이터용 M
73%사고실험: 중계 단계마다 핵심 제약의 10%가 빠지면, 세 번 거친 뒤 작업자에게 닿는 비율
2개의 상태이 글에서 가장 강조하는 구분: Worker Done과 Accepted
1개의 지표최적화 대상: 승인 산출물당 총비용과 시간

이 글은 AI 초안 셋과 필자의 초안을 합쳐 정리했고, 본문에 나오는 명령어는 2026년 11월 23일 기준 공식 문서와 대조했습니다. 다만 모든 명령을 같은 환경에서 직접 실행해 본 것은 아니니, 실제로 쓰기 전에 설치한 버전의 --help로 한 번 더 확인해 보시길 권합니다.

1. 병목은 코드에서 사람으로 옮겨 갔다#

에이전트를 여러 개 띄우면 코드는 금세 나옵니다. 진짜 문제는 그다음부터예요. 결과를 확인하고 방향을 정해 병합하는 사람이 전체 흐름에서 가장 느린 구간이 됩니다.

        A3["에이전트 3: 결과 완료"]

에이전트 하나만 쓸 때는 지시하고 결과를 확인하는 것으로 충분합니다. 그런데 여러 프로젝트에서 에이전트가 동시에 돌아가기 시작하면 사람에게 새로운 관리 업무가 따라붙습니다.

  1. 어느 에이전트가 지금 무슨 일을 하고 있는지 파악하기
  2. 멈춰 있거나 내 판단을 기다리는 작업 찾아내기
  3. 에이전트 사이에서 결과물과 맥락 옮기기
  4. 끝난 결과물의 품질 검증하기
  5. 후속 작업을 다시 배정하거나 마무리하기

일은 에이전트에게 맡겼는데, 정작 사람은 하루 종일 에이전트를 들여다보며 관리만 하게 됩니다. 이 글이 풀려는 문제가 바로 여기 있습니다.

2. 영상이 제안한 구조: 3계층과 코디네이터 보드#

개발동생 채널의 영상 「코디네이터 에이전트가 필요한 이유 | 내가 병목이면 보세요」 는 이 병목을 역할 계층으로 나누어 풀자고 제안합니다. 출발점은 단순해요. 창을 5개, 10개 띄워 놓아도 사람은 여러 창에 동시에 답하고 승인할 수 없기 때문입니다.

flowchart TD
    IN["외부 요청 (Slack, 메일, GitHub 이슈, 티켓)"] --> M["1계층: 매니저 에이전트 (선택)"]
    M --> C["2계층: 코디네이터 에이전트 (핵심)"]
    C --> B["코디네이터 보드 (칸반, 내 결정 카드)"]
    B <--> H["사람 (판단 및 승인)"]
    C -->|"난이도 A-D 배정, 계정 및 리소스 분산"| W1["3계층: 코딩 에이전트 A"]
    C -->|"상태 및 승인 대기 추적"| W2["3계층: 코딩 에이전트 B"]
    C -->|"병렬 세션 실행"| W3["3계층: 코딩 에이전트 C"]
  • 매니저 에이전트 (선택): 슬랙, 메일, GitHub 이슈, 고객 티켓에 흩어진 요청을 모아 일감으로 정리합니다. 시킬 일이 이미 명확하다면 건너뛰어도 됩니다.
  • 코디네이터 에이전트 (핵심): 일감을 어느 프로젝트와 세션에 맡길지 정하고, 병렬로 도는 작업 상태와 권한 승인 대기를 추적합니다. 난이도를 A부터 D까지 나누어 모델과 추론 강도(Effort)를 고르고, 여러 구독 계정의 사용량 여유와 기기 리소스를 살펴 작업을 나눕니다.
  • 코딩 에이전트: 실제 작업 세션에서 코드를 쓰고 수정합니다.

이 구조에서 가장 실전적인 장치는 보드입니다. 작업이 동시에 수십 개씩 돌면 채팅 기록만 훑어서는 검토하기 어렵습니다. 그래서 칸반 보드로 전체 현황을 한눈에 보고, 사람이 판단해야 할 안건만 「내 결정」 카드로 모아 처리합니다. 영상에서도 모든 계층이 누구에게나 필요한 것은 아니며, 코딩 에이전트를 동시에 여러 개 돌리고 있다면 코디네이터부터 도입해 보라고 권합니다. 이 구조를 실제 도구로 구현한 것이 Paseo용 coordinator-board 플러그인입니다(설치 방법은 8장에서 다룹니다).

3. 핵심 통찰: 관제, 추론, 검증을 분리하라#

영상 댓글에서는 두 입장이 뚜렷하게 부딪혔습니다. 한쪽에서는 계층과 에이전트가 늘어날수록 맥락이 빠져나가고 관리 비용만 몇 배로 커지며, 기능이 돌아가는 것과 결과물 품질은 별개라고 지적했습니다. 반대로 다른 쪽에서는 대형 프로젝트 3개만 동시에 돌려도 이런 관리 구조 없이는 몇 달을 버티기 어렵다고 맞섰어요. 규칙을 아무리 꼼꼼히 적어 두어도 결과물 품질이 떨어진다는 경험담도 이어졌습니다.

양쪽 이야기가 다 고개가 끄덕여지는 데에는 이유가 있습니다. ‘코디네이터’라는 한 단어 아래 성격이 완전히 다른 세 기능이 뒤섞여 있기 때문이에요. 찬성 쪽은 관제 기능의 효용을, 비판 쪽은 추론 중계의 위험을 이야기하고 있었습니다. 두 진영의 전제를 나란히 비교한 표는 글 끝 부록에 정리해 두었습니다.

flowchart LR
    subgraph Ctrl["관제 계층 (두껍게)"]
        C1["세션 상태 수집"]
        C2["blocked 알림 집계"]
        C3["모델 및 계정 한도 분산"]
    end
    subgraph Reason["추론 계층 (얇게)"]
        R1["원본 요구사항 파일 직접 전달"]
        R2["중간 재해석 최소화"]
    end
    subgraph Verify["검증 계층 (명시적으로)"]
        V1["사전 완료 기준과 테스트"]
        V2["독립 리뷰어 검토"]
        V3["사람의 최종 승인"]
    end
    Ctrl --> Reason --> Verify
  • 관제 계층은 두껍게 만듭니다. 세션 상태, 승인 대기(blocked) 알림, 사람이 답할 질문을 한 화면에 모아 주는 일은 계층 논쟁과 상관없이 생산성을 끌어올립니다. 범위가 명확한 작업의 모델 배정이나 구독 계정별 한도 분산도 사람이 매번 고민할 필요가 없는 기계적인 일입니다.
  • 추론 계층은 얇게 유지합니다. 매니저가 요약해서 코디네이터에게 넘기고, 코디네이터가 다시 작업 세션용 프롬프트를 새로 써 주는 다단계 구조는 전언 게임처럼 맥락을 조금씩 깎아 먹습니다.
  • 검증 계층은 명시적으로 둡니다. 품질 판정을 중간 에이전트에게 맡기지 않고 완료 기준, 테스트, 독립 리뷰, 사람의 승인으로 분리해 둡니다.

추론 중계가 왜 위험할까요? 요약은 본질적으로 정보가 줄어드는 손실 압축이기 때문입니다. 단계마다 핵심 제약의 90%만 살아남는다고 가정해도 두 번 거치면 81%, 세 번 거치면 73%만 작업자에게 전달됩니다. 더 큰 문제는 빠지는 내용이 무작위가 아니라는 점이에요. 요약할 때는 대개 ‘무엇을 할지’만 남기고 ‘무엇을 하지 말지’와 ‘왜 그렇게 해야 하는지’부터 덜어냅니다. 그래서 아키텍처 결정, 핵심 비즈니스 로직, 대외 보고서처럼 정성적 품질이 중요한 작업은 중간 에이전트가 지시를 다시 해석하지 못하도록 원본 요구사항 파일 경로를 작업 세션에 직접 넘겨야 합니다.

        S1["1차 요약: 매니저 (90% 유지)"]

4. 무엇을 사람이 직접 결정할까: 결정 필터#

도구를 고르기 전에 먼저 정해야 할 기준이 있습니다. 어디까지 에이전트에게 맡기고 어떤 결정을 사람이 직접 내릴지입니다. 영상이 제시한 기준이 가장 실용적이에요. 내가 무엇을 골라도 결과가 같은 일은 에이전트에게 맡기고, 내 선택에 따라 결과가 달라지는 결정만 보드에 올리는 방식입니다.

flowchart TD
    Q1{"내 선택에 따라 결과가 달라지는가?"}
    Q1 -->|"아니요"| R1["에이전트가 직접 결정하고 근거 기록"]
    Q1 -->|"예"| Q2{"되돌리기 어렵거나 영향 범위가 넓은가?"}
    Q2 -->|"아니요 (되돌릴 수 있음)"| R2["내 결정 카드로 비동기 응답"]
    Q2 -->|"예 (고위험, 광범위)"| R3["Decision Gate로 해당 작업 차단 (다른 작업은 계속 진행)"]

여기서 한 단계 더 나눕니다. 되돌리기 어렵거나 영향 범위가 넓은 결정은 해당 작업을 명시적으로 멈춰 두고, 관련 없는 다른 독립 작업은 계속 돌아가게 합니다. 에이전트가 같은 질문을 주기적으로 반복해서 묻게 두면 사람이 처리할 피로만 커집니다.

결정 유형예시처리 방식

결과는 달라지지만 되돌릴 수 있는 선택화면 문구, 리팩터링 범위「내 결정」 카드로 비동기 응답

Coordinator Board 역시 작업 폴더 삭제 같은 결정은 대신 처리하지 않고 담당자가 직접 판단하게 합니다. 도구를 만드는 쪽에서도 비슷한 경계선을 긋고 있는 셈입니다.

6. Herdr 실전: 상태를 보고, 막힌 곳만 처리한다#

Herdr는 터미널 멀티플렉서인 tmux를 코딩 에이전트 환경에 맞춰 다시 만든 도구입니다. Claude Code나 Codex 같은 기존 CLI 에이전트를 그대로 쓰면서, 각 화면(페인)이 지금 일하는 중인지, 내 답을 기다리는지, 작업이 끝났는지를 한눈에 보여 줍니다. 별도 플랫폼으로 갈아타지 않고 평소 터미널 습관 그대로 바로 시작할 수 있다는 점이 매력적입니다.

6.1 설치#

# 터미널 앱(TUI)
curl -fsSL https://herdr.dev/install.sh | sh   # 또는 brew install herdr

# 데스크톱 앱
curl -fsSL https://releases.herdr.dev/app/install.sh | sh

# 화면 없는 런타임 herdr-core (hc 명령)
curl -fsSL https://releases.herdr.dev/core/install.sh | sh

설치 스크립트는 실행하기 전에 내용을 한 번 읽어 보는 편이 안전합니다. 앞서 말씀드렸듯 터미널 앱과 데스크톱 앱은 세션을 공유하지 않으니, 처음에 둘 중 하나를 정하고 시작하는 편이 깔끔합니다.

6.2 상태 감지: 사이드바만 보고 점프한다#

tmux에서 창을 6개 띄워 놓으면 어느 에이전트가 멈췄는지 화면을 일일이 넘겨 확인해야 합니다. Herdr에서는 사이드바에 blocked가 뜬 페인으로 바로 건너뛸 수 있어요.

상태의미사람이 할 일
working작업 중없음
blocked승인, 입력, 결정이 필요함 (앱에서는 needs you)질문을 읽고 답한다
done끝났고 아직 확인하지 않음결과를 검토한다
idle확인을 마치고 대기 중다음 작업을 준다
unknown에이전트는 보이지만 상태를 분류하지 못함integration을 점검한다

상태를 읽는 방식은 앱에 따라 다릅니다. 터미널 앱은 현재 실행 중인 포그라운드 프로세스와 화면 출력 패턴을 보고 판단하고, herdr-core는 프로그램이 OSC 7501 프로토콜로 보내는 상태 신호를 받습니다. CLI 에이전트마다 상태를 알려 주는 수준이 다르므로, 자주 쓰는 에이전트는 공식 integration을 먼저 설치해 두는 것이 좋습니다.

herdr integration install claude
herdr integration install codex
herdr integration status
herdr agent explain reviewer --verbose   # 상태 판단 근거 확인

여기서 integration은 세션 ID를 기록해 재시작 뒤에도 대화를 이어 갈 수 있게 돕는 기능입니다. 권한 요청 프롬프트를 자동으로 승인해 주는 기능은 아니므로 오해하지 않는 편이 좋습니다.

사용할 때 주의할 함정도 하나 있습니다. Herdr의 기본 단축키 접두사(프리픽스 키)가 tmux와 같은 Ctrl+B입니다. 셸 설정(.zshrc 등)에서 페인이 열릴 때 tmux를 자동 실행하도록 해 두었다면 키가 겹치고, 포그라운드 프로세스가 tmux로 잡혀 안쪽 에이전트의 상태를 읽지 못합니다. Herdr를 쓸 때는 자동 tmux 진입 설정을 꺼 두세요.

6.3 독립 리뷰어 붙이기#

herdr-core의 hc 명령을 쓰면 리뷰어 에이전트를 백그라운드에 띄워 두고, 작업이 끝나길 기다렸다가 결과만 읽어 올 수 있습니다.

hc run --bg --name reviewer codex \
  "Review the current diff without editing files. Report bugs, regression risks, severity, and file locations."
hc wait reviewer              # 끝날 때까지 대기
hc read --lines 60 reviewer   # 마지막 60줄 읽기
hc send reviewer "Check authentication edge cases and missing tests."   # 추가 지시

터미널 앱에서는 페인을 나누어 같은 작업을 처리합니다. 스크립트로 자동화할 때는 현재 포커스된 페인에 기대지 말고, 페인 생성 응답 JSON에서 받은 ID나 에이전트 이름을 직접 지정하는 편이 안전합니다.

split=$(herdr pane split --current --direction right --cwd "$PWD" --no-focus)
review_pane=$(printf '%s\n' "$split" | jq -r '.result.pane.pane_id')
herdr agent start reviewer --kind codex --pane "$review_pane"
herdr agent prompt reviewer "변경된 diff를 리뷰하고 실행 가능한 지적만 보고해" --wait --timeout 120000
herdr agent read reviewer --source recent-unwrapped --lines 120

리뷰어를 따로 띄웠다고 해서 독립 검증이 저절로 완성되지는 않습니다. 구현 에이전트와 같은 전제를 그대로 공유하면 리뷰어도 같은 실수를 놓치기 쉽습니다. 리뷰어에게는 원래 요구사항, 변경된 코드, 테스트 결과를 함께 넘겨 주세요.

6.4 --wait의 함정#

herdr agent prompt --wait 명령은 ‘작업이 완전히 성공할 때까지’ 기다리지 않습니다. idle, done, blocked 가운데 가장 먼저 도달하는 안정 상태에서 바로 반환됩니다. 권한 승인이나 설계 질문(blocked)이 떴을 때도 명령이 끝난다는 뜻이에요. 코디네이터 세션이나 자동화 스크립트를 붙일 때는 반환된 상태를 먼저 확인하고, blocked라면 herdr agent read로 질문을 읽어 사람이 직접 의도를 갖고 답해야 합니다. 자동화 루프가 앞뒤 가리지 않고 y를 입력하게 만들면 위험합니다.

6.5 파일 기반 하드 게이트#

Herdr 위에서는 채팅으로 지시를 여러 번 옮겨 적기보다, Herdr를 실행과 관제 도구로만 쓰고 프로젝트 안의 파일을 기준 문서(단일 진실 공급원, Source of Truth)로 삼는 방식이 잘 맞습니다. 3장에서 말한 ‘추론은 얇게’ 원칙을 가장 직접적으로 적용하는 방법이에요.

  1. 실행 계약 파일을 먼저 정해 둡니다. 목표, 수정 허용 경로, 필수 테스트, 완료 조건을 EXECUTION.md 같은 파일에 적어 둡니다.
  2. 작업 창(페인)을 나란히 배치합니다. 구현 에이전트, 에디터, Lazygit이나 리뷰어를 상하 지시 관계 대신 옆자리처럼 평탄하게 둡니다.
  3. 단계마다 멈춰서 확인합니다. 구현 에이전트는 승인된 단계의 허용 경로 안에서만 작업하고 멈춥니다. 허용 경로 위반, 무단 커밋, 테스트 누락을 기계적으로 점검한 뒤 사람이 변경 단위(헝크)를 직접 확인하고 승인해야 다음 단계로 넘어갑니다.

6.6 끝낼 때는 종료 기록을 남긴다#

에이전트가 done 상태를 띄웠다고 곧바로 업무가 끝난 것으로 처리하지 않습니다. 검증(Review)을 통과한 작업만 맥락을 정리(Wrap up)한 뒤 닫습니다. 이 두 단계는 Herdr가 기본으로 제공하는 상태가 아니라 사용자가 직접 정해 두는 운영 절차입니다(10장에서 이어서 다룹니다).

## 작업 종료 기록
Issue: #42 로그인 오류
결과: 수정 및 재검증 완료
변경 파일: src/auth/session/...
테스트: 단위테스트 PASS, 통합테스트 PASS
리뷰: 미해결 Critical 0건
결정 사항: 기존 토큰 정책 유지
후속 작업: #48 세션 만료 안내
재개 조건: 통합테스트 재실패 또는 관련 요구사항 변경

이런 종료 기록을 남겨 두면 며칠 뒤 같은 작업을 다시 잡을 때 예전 대화 기록을 처음부터 뒤지지 않아도 됩니다.

Herdr 활용 판단. 에이전트 2-5개를 사람이 직접 감독하는 규모에서 가장 실용적입니다. 이 범위는 제품의 기술적 한계라기보다 사람이 감당하기 좋은 운영 복잡도를 고려한 권장 시작점이에요. 어디서 멈췄는지 빠르게 파악하는 데에는 강하지만, 반복 실행이나 결과물 검증 절차는 별도로 설계해야 합니다.

7. Orca 실전: 반복은 자동화하고, 위임은 구조화한다#

orca.dev의 Orca는 작업마다 독립된 git worktree를 만들고 그 안에서 CLI 에이전트를 돌리는 데스크톱 작업 공간입니다. Claude Code나 Codex 등 본인이 쓰는 구독을 그대로 연결할 수 있고, 모바일 앱과 원격 실행도 지원합니다. 이 글에서는 세 가지 기능에 집중해 보겠습니다. 줄 단위 diff 리뷰, 예약 자동화, 감독형 오케스트레이션입니다.

7.1 기본 흐름: 평탄한 병렬 실행#

brew install --cask stablyai/orca/orca   # orca만 쓰면 다른 cask가 설치된다

기본 사용 흐름은 단순합니다.

  1. GitHub나 Linear 이슈에서 바로 worktree를 만들고, 생성 창에서 브랜치와 에이전트를 고릅니다.
  2. 에이전트가 일하는 동안 다른 worktree로 넘어가 작업을 이어 갑니다. 끝나거나 입력이 필요할 때 알림이 옵니다.
  3. 화면 확인이 필요한 프런트엔드 작업이라면 에이전트 패널과 내장 브라우저를 나란히 분할합니다. Design Mode에서 화면 요소를 클릭하면 해당 HTML, 스타일, 셀렉터 정보가 에이전트 채팅에 바로 붙습니다. 말로 길게 설명하다 맥락이 어긋나는 일을 크게 줄여 줍니다.
  4. diff 화면에서 커밋 메시지와 PR 초안을 만들고, 실패한 CI 체크나 리뷰 코멘트는 다시 에이전트에게 넘겨 고칩니다.

7.2 품질 문제를 가장 깔끔하게 푸는 법: 줄 단위 diff 리뷰#

에이전트 작업이 끝나면 코디네이터에게 ‘품질 괜찮은지 봐 줘’라고 넘기기보다, diff 패널에서 바뀐 줄을 직접 보는 편이 훨씬 정확합니다. 고쳐야 할 줄에 코멘트를 달아 그 세션으로 바로 돌려보내면 에이전트는 추측 없이 짚어 준 지점만 수정합니다. 중간 에이전트의 재해석이 끼어들 틈이 없으므로, 3장의 ‘검증은 명시적으로’ 원칙을 가장 짧은 거리로 구현하는 방법입니다.

원격 SSH 호스트에 연결하고 모바일 알림을 켜 두면, 자리를 비운 사이에도 정말 결정이 필요할 때만 알림을 받을 수 있습니다. 내장 계정 스위처로 Claude와 Codex의 사용량과 리셋 시점을 확인하고 로그아웃 없이 계정을 바꾸는 기능도 실용적입니다.

7.3 예약 자동화: PR이 있을 때만 리뷰한다#

매일 PR을 확인해야 하는 루틴이 있더라도, 새 PR이 없는 날까지 에이전트가 돌면 토큰만 쓰고 똑같은 보고만 쌓입니다. Orca의 --precheck 옵션은 본격 실행 전에 셸 명령을 먼저 돌려 보고, 조건이 맞지 않아 실패(종료 코드 0 아님)하면 그 회차를 skipped run으로 기록한 뒤 건너뜁니다. 먼저 앱과 CLI가 정상 연결되었는지 orca status --json으로 확인하세요.

orca automations create \
  --name "Open PR review" \
  --trigger weekdays \
  --time 09:00 \
  --timezone Asia/Seoul \
  --precheck 'test "$(gh pr list --state open --json number --jq length)" -gt 0' \
  --prompt "Review open PRs. Check correctness, regression risks, and missing tests. Report findings with evidence. Do not merge." \
  --provider codex \
  --repo my-repo \
  --disabled \
  --json

orca automations list --json
orca automations run <automationId> --json            # 수동 테스트
orca automations runs --id <automationId> --json      # 실행 기록
orca automations edit <automationId> --enabled --json # 검증 후 활성화

처음에는 --disabled 상태로 만들어 수동 실행 결과를 확인한 뒤 활성화하는 편이 안전합니다. gh 명령을 쓰려면 GitHub CLI 설치와 인증이 미리 되어 있어야 합니다.

flowchart LR
    T["스케줄 트리거 (평일 09:00)"] --> PC{"precheck 실행 (열린 PR 존재?)"}
    PC -->|"실패 (0건)"| SK["skipped run 기록 후 종료"]
    PC -->|"성공 (1건 이상)"| CMP["이전 기록과 비교 (PR 번호, 마지막 커밋)"]
    CMP --> RUN["변경된 PR만 에이전트 리뷰 실행"]
    RUN --> LOG["PR 번호, 커밋, 검토 결과 기록"]

여기서 놓치기 쉬운 점이 하나 있습니다. precheck는 이번 회차를 실행할지 말지만 판단합니다. 같은 PR을 어제 이미 검토했는지, 그사이에 새 커밋이 들어왔는지는 스스로 알지 못합니다. 반복 작업을 제대로 운영하려면 PR 번호, 마지막으로 검토한 커밋, 검토 결과를 따로 기록해 두고 다음 회차에 비교하도록 설계해야 합니다.

7.4 감독형 오케스트레이션: Run, Task, Worker#

먼저 현재 지원 상태부터 확인할 필요가 있습니다. 이 기능은 아직 실험적이라 Settings → Experimental에서 켜야 하고, 공식 문서에서도 현재 실험적 패널과 스위치를 일시적으로 쓸 수 없다고 안내하고 있습니다. 예전 coordinator-start 같은 명령은 폐지되어 아무 동작도 하지 않습니다. 설치한 버전에서 작은 파일럿부터 동작 여부를 확인해 보세요.

개념역할
Run관련 작업을 묶는 네임스페이스이자 코디네이터의 수신함
Task작업 항목. pending, ready, dispatched, completed, failed, blocked 상태를 갖는다
DispatchTask를 터미널에서 한 번 시도한 단위
Messageworker_done, escalation, question, heartbeat 등 수신함 메일
Decision gate결정이 기록될 때까지 Task를 막는 질문
orca orchestration run-create --objective "Fix admin UI and verify regressions" --json
orca orchestration task-create --task-title "Fix admin UI" \
  --spec "Fix the reported UI issue and add regression tests. Report changed files and test evidence." --json

# 반환된 Task ID로 Worker 배정 (새 하위 worktree)
orca orchestration worker-start --task <taskId> --worktree new-child --name admin-ui-fix \
  --agent codex --setup run --json

# 완료, 에스컬레이션, 질문 메시지를 기다렸다가 처리 후 ack
orca orchestration check --wait --types worker_done,escalation,question --timeout-ms 900000 --json
orca orchestration check --ack <deliveryId> --wait --types worker_done,escalation,question --timeout-ms 900000 --json

# 결과를 검토한 뒤 터미널 정리
orca orchestration worker-release --dispatch <dispatchId> --json

worker-release는 Worker 출력을 보관한 뒤 코디네이터가 연 터미널만 정리하는 명령입니다. 품질 승인과는 별개의 리소스 정리 단계예요. 디버깅을 위해 터미널을 살려 두려면 worker-retain을 씁니다. Worker의 heartbeat 간격은 기본 5분이며 설정에서 1-60분 사이로 바꿀 수 있습니다.

에이전트가 임의로 정하면 안 되는 사항은 Decision Gate로 막아 둡니다. 공통 컴포넌트를 고칠지, 지금 보고 있는 화면만 고칠지 같은 선택이 대표적입니다.

orca orchestration gate-create --task <taskId> \
  --question "Apply the change to the shared component?" --options '["yes","no"]' --json
orca orchestration gate-resolve --id <gateId> --resolution "yes" --json

판단이 필요한 작업만 차단해 두고 나머지 독립 작업은 계속 진행하게 합니다(4장의 결정 필터와 같은 원리입니다). 다만 Gate는 승인 절차를 거는 부품일 뿐이므로, 누가 승인 권한을 갖는지와 감사 기록을 어디에 남길지는 별도로 정해 두어야 합니다.

7.5 모델과 추론 강도는 ‘요청’과 ‘적용’을 따로 본다#

worker-start에 --model과 --effort를 지정하면 해당 실행에만 적용됩니다. 이때 --effort는 --model을 함께 지정해야 하고, 그 모델이 지원하는 수준 안에서만 먹힙니다. 그래서 시작 영수증에 남는 launch.requested(요청한 값)와 launch.effective(실제 적용된 값)를 함께 기록해 두어야 나중에 비용과 품질을 정확히 비교할 수 있습니다. 계획, 구현, 독립 리뷰에 모두 같은 모델과 같은 추론 강도를 쓸 이유는 없습니다.

7.6 기준 브랜치를 통일한다#

worktree를 여러 개 동시에 돌릴 때는 시작 기준 브랜치를 하나로 맞추고, 병합이 끝난 worktree는 바로 정리하는 편이 좋습니다. 로그인, 권한, 공통 컴포넌트처럼 같은 파일을 건드리는 작업은 병렬로 맡기지 말고 순서를 나누세요. worktree는 파일 충돌은 막아 주지만 설계 충돌까지 막아 주지는 못합니다.

Orca 활용 판단. 매일 반복되는 이슈 점검, PR 리뷰, 테스트 실행에 가장 먼저 적용하기 좋습니다. UI를 눈으로 확인해야 하는 프런트엔드 작업에서도 줄 단위 리뷰 흐름이 매끄럽습니다. 감독형 오케스트레이션은 아직 실험적 단계이므로 작은 범위에서 먼저 검증해 보시길 권합니다.

8. Paseo 실전: 여러 프로젝트의 결정을 한 화면으로#

Paseo는 내 머신의 데몬 위에서 Claude Code, Codex, Copilot, OpenCode, Pi 같은 코딩 에이전트를 실행하고, 데스크톱, 모바일, 웹, CLI 어디서나 같은 세션에 접속할 수 있는 도구입니다. 휴대폰으로 결정 요청을 처리할 수 있고, 플러그인으로 자기 작업 방식에 맞는 보드를 붙일 수 있다는 점이 앞의 두 도구와 구별됩니다.

8.1 CLI로 얇게 자동화한다#

Paseo CLI는 앱이 쓰는 데몬에 직접 연결됩니다. 하위 세션을 띄우거나 정기 점검을 걸 때는 아래처럼 명시적인 명령으로 다루는 편이 맥락 추적에 유리합니다.

# 백그라운드로 독립 작업을 실행하고, 끝나기를 기다려 로그 확인
agent_id=$(paseo run --no-wait --quiet --title api-test "결제 API 예외 케이스 단위 테스트 추가")
paseo wait "$agent_id" --timeout 600
paseo logs "$agent_id" --tail 20

# 실행 중인 턴을 끊지 않고 방향만 보정
paseo send "$agent_id" --behavior steer "결제 게이트웨이 모킹은 기존 fixtures 파일 기준을 따라줘"

# 반복 점검 스케줄
paseo schedule create --every 30m --cwd ~/dev/my-app "실패한 통합 테스트 로그를 점검하고 요약만 남겨줘"

paseo ls --json

여기서 기억해 둘 세부 동작이 있습니다. paseo send는 누가 보냈느냐에 따라 기본 동작이 다릅니다. 에이전트가 보내면 대기열에 넣는 queue, 사람이 보내면 진행 중인 작업을 멈추는 interrupt로 동작해요. 실행 중인 에이전트의 흐름을 끊지 않고 방향만 살짝 보태고 싶다면 --behavior steer를 꼭 붙여 주세요. 작업을 별도 worktree에서 돌리는 옵션(--new-workspace worktree 등)은 버전마다 이름이 달라져 왔으므로 paseo run --help로 확인하는 편이 정확합니다.

8.2 오케스트레이션 스킬: 인계하고, 의견을 듣는다#

앱의 Settings → 호스트 → Agents → Orchestration skills에서 선택하거나, 에이전트가 도는 머신에서 npx skills add getpaseo/paseo를 실행해 스킬을 추가합니다.

스킬하는 일
/paseo에이전트, 워크스페이스, 스케줄, 하트비트 관리법 참조. 다른 스킬의 기본 레퍼런스
/paseo-handoff관련 파일, 진행 상황, 결정, 제약, 완료 기준을 담은 브리핑과 함께 다른 에이전트에게 작업을 넘김
/paseo-advisor설계, diff, 질문을 두고 다른 에이전트의 의견을 받음. 파일을 고치지 않음
/paseo-committee어려운 문제를 두 에이전트가 독립적으로 분석. 가능하면 다른 제공사 계열을 고름

실제로 구현을 넘기거나 검토를 요청할 때는 이렇게 씁니다.

/paseo-handoff 현재 인증 오류 수정 작업을 구현 에이전트에게 넘겨 줘. 변경 대상 파일, 확인된 원인, 수정 범위, 테스트 기준, 미해결 질문을 포함하고 별도 worktree에서 작업하도록 해.

/paseo-advisor 이번 인증 로직 변경에서 누락된 예외 처리, 회귀 가능성, 보안 문제를 확인해 줘. 파일과 코드 위치를 근거로 제시하고 코드는 수정하지 마.

handoff는 대화 전문을 통째로 복사하는 것보다 깔끔하지만, 결국 요약이라는 점은 같습니다. 브리핑에서 중요한 제약이 하나라도 빠지면 새 에이전트도 엉뚱한 방향으로 갈 수 있으니 handoff 브리핑 자체도 검토 대상으로 챙기는 편이 안전합니다.

8.3 코디네이터 보드 설치와 구성#

Paseo 0.16.2 이상이 설치된 호스트에서 Settings → Plugins → Enable plugins를 켠 뒤 아래 명령으로 설치합니다.

paseo plugin install devbrother2024/coordinator-board
paseo plugin ls coordinator-board              # 상태가 running인지 확인
paseo plugin update coordinator-board --check  # 새 릴리스 미리보기
paseo plugin update coordinator-board          # 검토 후 적용

플러그인은 계속 업데이트되면서 바뀝니다. 설치한 버전과 시점을 메모해 두면 나중에 동작이 달라졌을 때 원인을 찾기 쉽습니다. 설치한 뒤에는 다음 순서로 설정합니다.

  1. 호스트를 고릅니다. 데몬이 떠 있는 기기 가운데 총괄할 호스트를 정합니다. 코디네이터는 자기 호스트에서만 작업자를 만들 수 있습니다.
  2. 관리할 프로젝트를 고릅니다. 처음에는 민감하지 않은 프로젝트 한두 개로 시작하는 편이 안전합니다.
  3. 코디네이터를 만듭니다. Start with recommended settings를 고르면 생성 전에 모델과 도구 권한 모드가 표시됩니다. 권장 설정은 Claude Code에서 Auto 모드, Codex에서 Auto-review를 우선 적용하므로, 민감한 저장소라면 권한 모드를 꼭 확인하고 넘어가세요. 이미 잘 세팅된 세션이 있다면 그 세션을 코디네이터로 지정해도 됩니다.
  4. 등급별 모델을 정합니다. 바로 아래 8.5에서 자세히 살펴봅니다.

코디네이터의 역할은 작업 분류, 배정, 결과 및 미결정 항목 수집으로 한정하고 실제 구현은 별도 작업자에게 맡깁니다. 3장에서 정리한 ‘관제는 두껍게, 추론은 얇게’ 원칙을 보드 설정으로 옮긴 구성입니다.

8.4 다이제스트와 결정 카드#

Request digest는 코디네이터가 최근 대화 발췌를 훑어보고 사람의 결정이 필요한 항목만 골라 기록하게 하는 기능입니다. 보드에는 판단 근거도 함께 뜹니다. 코디네이터 헌장이나 요청 문구에 아래 같은 기준을 넣어 두면 카드의 품질이 한결 좋아집니다.

관리 중인 프로젝트의 세션을 확인하고 사람이 결정해야 하는 항목만 정리해 줘. 각 항목에는 원본 세션, 질문, 선택지, 권장안, 판단 근거를 포함해. 단순 진행 보고와 에이전트가 스스로 해결할 수 있는 기술적 문제는 제외해.

결정 카드 기능쓰임새

8.5 등급 A-D와 M: 난이도별 모델 라우팅#

보드는 작업 등급 A-D마다 제공사와 모델을 정하고, M 등급은 코디네이터를 새로 만들거나 교체할 때 씁니다. 아래 표는 영상 화면에 나온 등급 정의와 모델 배정 예시입니다. 모델 목록은 계속 바뀌므로 구조만 참고하시고 본인 구독 구성에 맞춰 조정해 보세요.

등급작업 성격배정 예시 (영상 화면 기준)
A구조를 결정하는 작업. 고성능 모델 필요Fable 5.2 Xhigh, Opus 5.5 Max, GPT 6.2 Astra Xhigh
B설계가 필요하거나, 원인이 불명확하거나, 위험이 큰 작업Fable 5.2 High, Opus 5.5 Xhigh, GPT 6.2 Astra High
C수정 범위나 완료 조건이 정해진 작업Opus 5.5 High, GPT 6.2 Sol High, Sonnet 5.5 High, Gemini 4 Neon, Hydrogen, Carbon, Argon
D기존 자료를 살펴보고 요약, 정리하는 단순 작업Sonnet 5.5 Medium, GPT-6 Luna High, Gemini 4 Hydrogen
M코디네이터 생성, 교체설정에서 지정

이 표에서 눈여겨볼 포인트는 세 가지입니다.

  1. A가 가장 무거운 등급입니다. A는 구조 결정, D는 요약과 정리입니다. 순서를 거꾸로 잡으면 가장 중요한 결정에 가장 가벼운 모델이 배정되니 주의하세요.
  2. 등급은 모델 교체와 함께 추론 강도 조절을 포함합니다. 예를 들어 Opus 5.5는 A에서 Max, B에서 Xhigh, C에서 High로 세 등급에 걸쳐 쓰입니다. 같은 모델이라도 얼마나 깊게 생각하게 할지에 따라 등급이 갈립니다.
  3. A와 B는 3장의 ‘추론은 얇게’ 원칙이 가장 중요한 등급입니다. 구조와 설계를 정하는 작업은 코디네이터가 요약해서 넘기지 말고 원본 요구사항 파일 경로를 작업 세션에 직접 건네야 합니다. 반대로 C와 D처럼 범위가 뚜렷한 작업이 기계적인 라우팅에 잘 맞습니다.

코디네이터(M)에 늘 가장 비싼 모델을 배정할 필요는 없습니다. 역할이 상태 수집과 작업 배정 위주라면 가벼운 모델부터 시험해 보고, 추천 답변 작성까지 맡길수록 모델 품질을 높이는 편이 합리적입니다. 사용량 한도가 찼다고 모델을 기계적으로 갈아 끼우는 것도 조심해야 합니다. 모델이 바뀌면 도구 지원 범위와 판단 품질이 함께 달라질 수 있기 때문입니다.

8.6 PR은 보드에서 병합할 수 있지만#

Merge on board는 저장소, 브랜치, 커밋을 확인한 뒤 병합을 진행하고, 그사이에 커밋이 바뀌거나 요구 조건이 실패하면 다시 검토하게 합니다. 편리하지만 그래도 병합과 품질 승인은 별개 단계로 두는 편이 안전합니다.

  1. 작업자가 코드를 고치고 PR을 만듭니다.
  2. 자동 테스트와 정적 분석을 돌립니다.
  3. 독립 리뷰어가 요구사항과 변경 코드를 검토합니다.
  4. Critical 결함과 필수 테스트 결과를 확인합니다.
  5. 사람이 최종 승인하고 병합합니다.

8.7 도입 전 확인할 점#

  • 비용: 보드를 열어 보는 것만으로는 모델이 돌지 않습니다. 하지만 자동 답변 기능은 수신 세션의 모델을 실행해 사용량을 소모합니다. 호스트별로 끌 수 있으니 처음에는 꺼 두고 추천 답변을 사람이 검토해 보내세요.
  • 기기 범위: 코디네이터는 자기 호스트에서만 작업자를 띄웁니다. Windows 작업은 Windows 호스트의 보드에서 요청해야 합니다.
  • 데이터: 선택, 판단, 메모는 호스트의 로컬 플러그인 데이터에 저장됩니다. 질문과 근거 원문이 평문 JSON으로 남는다는 점을 감안하세요.
  • 보안: Paseo 플러그인은 데몬 머신 권한으로 실행됩니다. 업무 환경에 붙이기 전에는 소스 코드, 의존성, 접근 권한을 먼저 검토해야 합니다.
  • 성숙도: 개인이 공개한 초기 프로젝트입니다. 민감하지 않은 프로젝트에서 먼저 시험해 보세요.

Paseo 활용 판단. 여러 프로젝트를 동시에 돌리면서 판단 요청이 여기저기 흩어지는 환경에 가장 잘 맞습니다. 프로젝트별 상태와 사람의 결정을 한곳에 모아 주는 기능은 강력하지만, 결과물의 품질까지 자동으로 보증해 주지는 않습니다.

9. 상황별 조합: 세 도구를 모두 설치할 필요는 없다#

무슨 도구를 설치할지보다 먼저 정해야 할 것은 어떤 결정을 사람이 직접 내릴지입니다. 그 기준이 서고 나면 중심 도구는 작업 규모와 반복성에 따라 고르면 됩니다.

flowchart TD
    START{"운영 상황과 작업 성격"}
    START -->|"한 프로젝트, 에이전트 여러 개"| SA["시나리오 A: Herdr 중심 (GitHub Issue 원본, worktree, 독립 리뷰어)"]
    START -->|"매일 반복되는 점검과 리뷰"| SB["시나리오 B: Orca 중심 (Scheduled Automations, precheck, 상태 비교)"]
    START -->|"대형 프로젝트 3개 이상 병렬"| SC["시나리오 C: Paseo 중심 (프로젝트별 작업자, Coordinator Board 결정 수집)"]
  • 시나리오 A, 한 프로젝트에서 에이전트 여러 개: GitHub Issue를 작업 원본 기록으로 두고 작업마다 worktree를 나눕니다. 구현이 끝나면 독립 리뷰어에게 넘기고, 통과하면 PR을 병합한 뒤 Issue에 종료 기록을 남깁니다. 이 규모에서는 상위 코디네이터가 없어도 충분히 돌아갑니다.
  • 시나리오 B, 매일 반복되는 운영 작업: 미해결 이슈와 PR 점검, 새 PR의 테스트 누락 확인, 의존성 점검, 테스트 실패 기록 분석 같은 루틴이 대상입니다. 주기적으로 돌리는 것 자체보다, 실행 뒤 어떤 상태를 기록하고 다음 회차에 어떻게 이어받을지를 설계하는 일이 핵심입니다.
  • 시나리오 C, 대형 프로젝트 3개 병렬: 프로젝트마다 작업자를 두고, 코디네이터 보드는 사람의 결정만 모읍니다. 프로젝트 안의 작업자들 위에 또 다른 코디네이터 계층을 덧댈 이유는 없습니다. 범위가 명확하고 독립적인 작업은 작업자에게 직접 배정하세요.

세 도구를 함께 쓸 때의 운영 경계#

Herdr, Orca, Paseo는 실행 환경과 상태 관리 체계가 서로 다릅니다. Orca에서 만든 Task와 Worker가 Paseo 보드에 자동으로 뜨지 않고, Herdr 세션도 별도 연결 없이는 Paseo가 관리하지 않습니다. 여러 도구를 섞어 쓸 계획이라면 역할 경계부터 분명히 정해 두어야 합니다.

책임운영 원칙
작업 원본GitHub Issues 등 하나의 시스템
실행 관리작업 단위마다 도구 하나를 지정
코드 변경독립 worktree 사용
완료 근거테스트와 리뷰 결과를 PR에 기록
판단 관리결정권자와 승인 기록을 명시
후속 작업기존 Issue 갱신 또는 새 Issue 생성

특히 같은 코드를 여러 도구의 코디네이터가 동시에 수정하게 두면 안 됩니다. 지시가 중복되고, 상태가 충돌하며, 실행 이력도 끊어집니다.

10. 품질은 검증 루프에서 나온다#

관제 도구를 잘 갖추면 에이전트가 어디서 멈췄는지 쉽게 눈에 들어옵니다. 하지만 그것만으로 좋은 결과물이 보장되지는 않아요. 빌드가 성공했더라도 요구사항을 잘못 이해했을 수 있고, 테스트가 통과했더라도 중요한 예외가 빠져 있을 수 있습니다. 문서가 그럴듯하게 완성되어도 근거가 약하거나 현업에서 쓰기 어려운 내용일 수 있습니다. 계층은 관제 비용을 줄이는 수단일 뿐 품질을 올려 주는 장치가 아니므로, 품질 검증은 작업 실행과 따로 떼어 설계해야 합니다.

10.1 구현 전에 완료 기준을 정한다#

‘로그인 오류를 고쳐 줘’처럼 막연하게 넘기기보다 아래처럼 기준을 먼저 적어 줍니다.

작업: 로그인 오류 수정

완료 기준
- 정상 계정 로그인 성공
- 잘못된 비밀번호에서 적절한 오류 응답
- 만료된 세션의 재인증 처리
- 기존 권한 검증 로직 유지
- 관련 자동 테스트 통과

제약 조건
- 인증 방식 변경 금지
- 기존 API 응답 형식 유지
- 테스트를 임의로 삭제하거나 비활성화하지 않음

보고 항목
- 변경 파일
- 테스트 명령과 결과
- 미해결 문제
- 요구사항과 다르게 해석한 부분

완료 기준은 작업 전에 미리 적어 두어야 합니다. 에이전트가 일을 마친 뒤 자기가 구현한 결과에 맞춰 기준을 슬쩍 바꾸는 일을 막기 위해서예요. 마지막 보고 항목인 ‘요구사항과 다르게 해석한 부분’이 특히 쓸모가 큽니다. 3장에서 짚은 맥락 유실이 여기서 가장 먼저 드러납니다.

10.2 리뷰어는 구현자와 독립적으로 검토한다#

리뷰어에게는 구현 에이전트의 요약 설명만 주지 말고 원래 요구사항, 변경 전후 코드, 테스트 결과를 함께 건네세요. 가능하면 다른 제공사의 모델을 쓰는 편이 같은 편향을 줄이는 데 도움이 됩니다.

변경 코드가 원래 요구사항을 충족하는지 확인해. 구현자의 설명이 맞다는 전제로 검토하지 마. 회귀 위험, 누락된 예외, 보안 문제를 찾아 파일 위치와 근거를 제시해. 확인하지 못한 사항은 추정이라고 표시하고 코드는 수정하지 마.

리뷰가 ‘통과’를 선언해 주는 것보다, 무엇을 직접 확인했고 무엇을 확인하지 못했는지가 투명하게 남는 편이 훨씬 중요합니다.

10.3 정성적 산출물에는 다른 검증이 필요하다#

에이전트가 만드는 결과물이 늘 코드만은 아닙니다. 기획서, 보고서, 화면 설계서, 심사 기준, 운영 정책 같은 문서는 자동 테스트로 품질을 판별하기 어렵습니다. 댓글에서 나온 ‘기능적으로 돌아가는 것과 품질은 다른 문제’라는 지적이 가장 정확히 맞아떨어지는 영역이에요.

품질 항목검증 방법
사실 정확성원문 자료와 근거 대조
요구사항 적합성승인된 기준과 항목별 매핑
논리 일관성서로 모순되는 주장과 누락 확인
현업 사용성실제 사용자 시나리오로 검토
설명 가능성결론의 근거와 판단 과정 확인
변경 추적성기존 문서와 변경 내역 비교

업무 규칙이나 정책 판단이 담긴 결과물은 AI 리뷰어가 적합하다고 판정했더라도 최종 책임자가 직접 확인해야 합니다. 기술 정확성 담당과 업무 요구사항 담당처럼 관점이 다른 리뷰어 둘을 두는 것도 방법입니다. 다만 리뷰어가 늘어날수록 비용도 커지니, 작업의 위험 수준에 맞춰 검증 강도를 조절하세요.

10.4 Done과 Accepted를 구분한다#

이 글에서 딱 하나만 챙겨야 한다면 바로 이 구분입니다.

flowchart LR
    IN["작업 시작 (완료 기준과 제약 정의)"] --> RUN["구현 실행 (에이전트)"]
    RUN --> WD["Worker Done (에이전트 완료 선언)"]
    WD --> REV{"독립 검증 (테스트, 독립 리뷰, 사람 검토)"}
    REV -->|"결함 또는 기준 미달"| RUN
    REV -->|"품질 기준 통과"| ACC["Accepted (최종 승인)"]
    ACC --> WRAP["Wrap up (종료 기록과 재개 조건 저장)"]

Worker Done은 에이전트가 작업을 마쳤다고 알린 상태이고, Accepted는 미리 정해 둔 품질 기준을 통과해 승인된 상태입니다. 둘을 하나로 취급하면 겉으로는 작업 완료율이 높아 보이지만, 뒤에서 재작업과 결함 수정에 더 많은 시간을 쓰게 됩니다. Herdr의 done, Orca의 worker_done, 보드의 ‘답변 보냄’은 모두 왼쪽 칸(Worker Done)에 해당합니다. 오른쪽 칸(Accepted)으로 넘기는 일은 어느 도구도 대신해 주지 않습니다.

11. 성과는 무엇으로 재나#

에이전트 수나 실행 횟수는 얼마나 바쁘게 돌아갔는지만 보여 줍니다. 진짜로 줄여야 할 대상은 승인된 결과물 하나를 얻기까지 들어간 총비용과 시간입니다.

승인 산출물당 총비용 = (모델 사용료 + 사람의 검토와 수정 시간 × 시간당 비용) ÷ Accepted 산출물 수

분자에 사람의 시간이 들어간다는 점이 핵심입니다. 에이전트가 저렴한 모델로 코드를 뽑아냈더라도 사람이 다시 분석하고 고치는 데 시간을 쏟았다면 전체 비용은 오히려 커집니다. 분모가 Worker Done이 아니라 Accepted라는 점도 놓치지 마세요.

지표확인할 질문
승인 산출물 수품질 기준을 통과한 결과물이 얼마나 늘었나
재작업률완료 후 수정 요청이 얼마나 생겼나
사람 개입 횟수사람이 직접 개입한 횟수가 줄었나
판단 대기 시간사람의 결정이 없어 멈춘 시간은 얼마인가
맥락 복구 시간중단된 작업을 다시 이해하는 데 얼마나 걸리나
승인 산출물당 비용모델 사용료와 사람의 검토 비용을 합치면 얼마인가
결함 재발률이미 해결한 문제가 다시 나오는가

도입 전후를 비교할 때는 작업의 규모와 난이도를 맞추어야 합니다. 간단한 수정 10건과 복잡한 아키텍처 변경 1건을 같은 저울에 올려 비교할 수는 없으니까요. 8장에서 살펴본 A-D 등급을 그대로 비교 단위로 쓰면 훨씬 정리하기 편합니다.

12. 도입 로드맵: 한 단계씩 넓힌다#

세 도구를 한꺼번에 도입하거나 억지로 이어 붙일 필요는 없습니다. 효과를 확인하기 가장 쉬운 단계부터 시작해서, 각 관문을 통과할 때만 다음 단계로 넓혀 가면 됩니다.

flowchart LR
    S1["1단계: 완료 기록 정비 (Issue 연결, 종료 기록)"]
    G1{"관문 1: 기록과 재개 효과 확인"}
    S2["2단계: 반복 작업 1건 자동화 (precheck, 수동 검증)"]
    G2{"관문 2: 중복 없이 안정적 보고"}
    S3["3단계: 비민감 프로젝트 1-2개 보드 테스트"]
    G3{"관문 3: 재작업률과 개입 시간 개선"}
    S4["4단계: 품질 지표 기준으로 범위 확대"]
    S1 --> G1 --> S2 --> G2 --> S3 --> G3 --> S4
  1. 완료 기록부터 정비합니다. 지금 쓰던 실행 환경은 그대로 두고 모든 작업에 Issue를 연결합니다. 작업이 끝나면 변경 파일, 테스트 결과, 남은 문제, 재개 조건을 빠짐없이 남깁니다. 단순해 보이지만 효과를 가장 빠르게 체감할 수 있습니다.
  2. 반복 작업 하나만 자동화합니다. 매일 손으로 확인하던 업무 중 하나를 골라 읽기 전용 점검과 보고부터 붙입니다. precheck로 실행 조건을 제한하고, 비활성 상태에서 수동 검증을 마친 뒤 활성화합니다. 재시도, 중복 실행 방지, 이전 결과와 비교가 필요한지도 이 단계에서 확인합니다.
  3. 판단 대기가 흩어지기 시작하면 보드를 시험합니다. 모든 프로젝트를 한꺼번에 연결할 필요는 없습니다. 민감하지 않은 프로젝트 한두 개에서 결정 카드와 원본 세션 연결이 매끄럽게 동작하는지 살펴봅니다. 추천 답변을 사람이 확인하지 않고 자동 전송하는 설정은 초기에 피하세요.
  4. 품질 지표로 확대 여부를 결정합니다. 일정 기간 운영해 본 뒤 재작업률, 사람 개입 시간, 리뷰에서 잡은 결함, 승인 산출물당 비용을 비교합니다. 관제 도구가 늘었는데도 사람이 직접 챙겨야 할 항목이 줄지 않는다면 도구보다 운영 방식부터 다시 돌아보아야 합니다.

마무리: 코디네이터는 적게, 검증은 명확하게#

멀티 에이전트를 운영한다고 해서 깊은 계층 구조가 꼭 필요한 것은 아닙니다. 작업이 서로 독립적이고 범위가 명확하다면 사람이 작업자에게 직접 배정하는 것으로도 충분합니다. 코디네이터가 힘을 발휘하는 순간은 여러 프로젝트에서 판단 요청이 동시에 쏟아질 때예요. 그때도 코디네이터는 지시를 다시 쓰는 중간 관리자 역할보다, 상태와 결정 대기열을 모아 주는 관제판에 머무는 편이 낫습니다.

어느 도구를 고르든 아래 세 가지는 오늘 바로 적용할 수 있습니다.

  1. 모든 작업에 시작 전 완료 기준을 적어 둡니다.
  2. 사람의 판단이 필요할 때만 명시적으로 작업을 멈추고 묻습니다.
  3. 작업자의 완료 선언(Worker Done)과 검증을 마친 승인(Accepted)을 구분합니다.

그다음에도 관제 부담이 크다면 보드와 자동화를 조금씩 넓히면 됩니다. 상태 추적, 권한 대기열 집계, 계정과 기기 분산 같은 기계적인 관제는 도구에 맡겨 두고, 의도를 정의하고 결과물의 품질을 판정하는 자리는 사람이 가장 가까운 거리에서 직접 쥐고 있어야 합니다. 좋은 오케스트레이션은 에이전트를 더 많이 돌리는 구조가 아니라, 사람의 한정된 직렬 주의력을 가장 가치 있는 결정에만 쓰게 해 주는 구조입니다.

바로 쓰는 체크리스트#

  • 작업을 맡기기 전에 완료 기준, 제약 조건, 보고 항목을 적었다.
  • 정성적 품질이 중요한 작업은 원본 요구사항 파일을 작업 세션에 직접 넘겼다.
  • 내 선택에 따라 결과가 달라지는 결정만 카드로 올리고, 되돌리기 어려운 결정은 해당 작업을 차단했다.
  • 구현 에이전트와 리뷰 에이전트를 분리했다.
  • 자동화 루프가 blocked 상태에서 무작정 승인하지 않는다.
  • 코디네이터 자동 답변을 정성적 판단에 쓰지 않는다.
  • Worker Done과 Accepted를 다른 상태로 관리한다.
  • 작업을 닫을 때 종료 기록과 재개 조건을 남겼다.
  • 반복해서 걸리는 실수는 규칙 문서 대신 테스트나 린트 같은 검사 항목으로 옮겼다.

부록. 댓글 논쟁 상세 비교#

두 진영이 전제하는 작업 성격과 품질 기준을 나란히 놓아 보면 차이가 뚜렷해집니다. 에이전트 수가 적을 때는 계층을 최소화하고 품질에 집중하는 편이 맞고, 여러 프로젝트를 병렬로 돌릴 때는 최소한 내 결정만 모아 주는 보드가 필요합니다.

구분병렬 관제 관점 (영상과 댓글 B)품질과 맥락 관점 (댓글 A, C)
핵심 병목여러 세션의 상태 추적, 컨텍스트 스위칭 피로중간 계층에서 생기는 맥락 손실과 산출물 품질 하락
전제하는 작업대형 프로젝트 여러 개를 동시에 굴리는 개발과 운영설계, 기획, 문서, 정책 판단처럼 정성적 완성도가 중요한 작업
품질의 정의테스트 통과, 빌드 성공, PR 확인 같은 명확한 완료 조건의도, 일관성, 현업 적합성까지 맞는 정성 평가
현업에서 맞는 지점병렬 세션이 여러 개를 넘으면 통합 관제판 없이는 사람이 먼저 지친다계층이 깊어질수록 요약과 재해석을 거치며 원문의 핵심이 빠진다
놓치기 쉬운 지점코디네이터에게 최종 검증까지 맡기면 품질 저하를 놓친다단일 세션의 논리를 대규모 병렬 운영에 그대로 적용하기 어렵다

비판 측의 가장 날카로운 지적은 품질입니다. 정성적 기준이 들어가는 순간, 중간 에이전트는 ‘규칙을 대략 지켰고 그럴듯해 보인다’는 이유로 완성도가 떨어지는 결과를 통과시켜 버립니다. 반대로 병렬 세션을 매일 여러 개 돌려 본 사람이라면, 어느 세션이 멈췄고 어느 세션이 권한 승인을 기다리는지 창마다 눌러 확인하는 일이 하루 에너지를 다 갉아먹는다는 주장에도 자연스럽게 공감하게 됩니다.
